# 1C-compatible catalog model

Документ фиксирует, как проектировать каталог ShopsBox так, чтобы будущий модуль интеграции с 1С не требовал переделывать ядро.

1С для ShopsBox считаем главным интеграционным ориентиром для российского ecommerce. Остальные интеграции важны, но модель каталога, цен и остатков не должна конфликтовать с 1С-логикой.

## Главный вывод

Нельзя строить каталог как одну плоскую таблицу `products` с ценой и остатком внутри товара.

Правильная целевая модель:

- `products` - номенклатура, то есть общее описание товара;
- `product_variants` - характеристика/вариант, то есть фактическая продаваемая единица;
- `prices` - отдельный регистр цен;
- `inventory_levels` или `stocks` - отдельный регистр остатков;
- `stock_locations` - склады;
- `product_specifications` и `product_specification_items` - будущая модель комплектов/составов;
- integration mapping - связь внутренних сущностей ShopsBox с GUID из 1С.

## Сравнение с текущей моделью ShopsBox

В документах ShopsBox уже заложена правильная ecommerce-основа:

- `products`;
- `product_variants`;
- `inventory_items`;
- `stock_locations`;
- `inventory_levels`;
- `inventory_reservations`.

Это хорошо совпадает с 1С-подходом: товар отдельно, характеристика отдельно, остатки отдельно.

Текущая MVP-реализация в коде пока проще: есть `products` и `categories`, без вариантов, отдельных цен, складов и регистров. Это допустимо для раннего CRUD и витрины, но следующий шаг каталога должен двигаться к 1С-совместимой модели, а не наращивать плоские поля в `products`.

## GUID из 1С

В 1С ключевые сущности приходят с GUID. Для синхронизации нельзя искать товары по названию, артикулу или slug.

Профессиональное правило для ShopsBox:

- внутренний `id` ShopsBox остается нашим UUID;
- GUID из 1С храним как внешний идентификатор;
- уникальность внешнего идентификатора проверяем в пределах магазина и источника интеграции.

Не стоит жестко делать GUID 1С единственным primary key во всех таблицах ядра. Причины:

- часть товаров может быть создана вручную в ShopsBox до подключения 1С;
- у клиента может быть несколько источников данных;
- будущие интеграции кроме 1С тоже будут приносить свои external id;
- внутренние связи ShopsBox должны жить даже при переподключении интеграции.

Лучший вариант:

```text
external_entity_links
  id
  store_id
  source_code        # 1c, moysklad, manual_import
  entity_type        # product, product_variant, price_type, stock_location, unit
  entity_id          # внутренний UUID ShopsBox
  external_id        # GUID/код внешней системы
  external_payload_hash
  synced_at
```

Для 1С можно дополнительно держать явные поля `external_1c_uuid` на горячих таблицах, если это ускорит массовый импорт. Но главным правилом остается: внешняя система не должна ломать внутреннюю идентичность ShopsBox.

## Products: номенклатура

Целевая таблица `products` должна хранить общие признаки номенклатуры:

- `id`;
- `store_id`;
- `product_type_id` или `type_code`;
- `base_unit_id`;
- `name`;
- `full_name`;
- `slug`;
- `description`;
- `has_variants`;
- `status`;
- `created_at`;
- `updated_at`.

Что важно: цена, остаток и склад не должны быть колонками `products`.

## Product variants: характеристики/SKU

`product_variants` должна стать основной продаваемой единицей.

Целевые поля:

- `id`;
- `product_id`;
- `sku`;
- `barcode`;
- `name`;
- `attributes`;
- `status`;
- `position`;
- `created_at`;
- `updated_at`.

`attributes` можно хранить как JSON для простого приема характеристик из 1С, но фильтры и SEO лучше позже нормализовать через `product_options`, `product_option_values`, `variant_option_values`.

Простое правило: даже если товар без размера и цвета, у него должен быть один вариант.

## Цены как регистр

Для 1С-совместимости цена не должна быть единственным полем `price` у товара.

Нужны:

```text
price_types
  id
  store_id
  code
  name
  currency
  is_default

prices
  id
  store_id
  product_id
  variant_id
  price_type_id
  value
  currency
  starts_at
  updated_at
```

На MVP можно показывать одну розничную цену, но хранить направление нужно так, чтобы позже добавить опт, город, канал продаж или период действия.

## Остатки как регистр

Остатки уже хорошо ложатся на текущую плановую модель ShopsBox:

```text
stock_locations
inventory_items
inventory_levels
```

Для 1С важно, чтобы остаток был связан со складом и вариантом товара, а не лежал в `products.quantity`.

`inventory_levels` должен уметь хранить:

- доступное количество;
- резерв;
- входящее количество;
- дату последней синхронизации.

## Спецификации и комплекты

Для MVP спецификации не нужны в интерфейсе, но в модели их стоит держать как будущий контур, чтобы не упереться в комплекты.

Целевые таблицы:

```text
product_specifications
  id
  store_id
  product_id
  variant_id
  name
  is_active
  created_at
  updated_at

product_specification_items
  id
  specification_id
  material_product_id
  material_variant_id
  quantity
  unit_id
```

Это пригодится для наборов, комплектов и производственных сценариев.

## Единицы измерения и виды номенклатуры

Чтобы 1С-импорт не размазывал служебные значения строками, нужны справочники:

```text
measurement_units
  id
  store_id
  code
  name
  short_name

product_types
  id
  store_id
  code
  name
```

Для раннего MVP их можно не выводить в админке, но не стоит закладывать `unit = "шт"` как простую строку в товаре.

## Журнал обмена

Модуль 1С должен иметь свой журнал обмена:

```text
integration_sources
integration_exchange_runs
integration_exchange_items
```

Минимальный смысл:

- какой источник синхронизировался;
- когда начался и закончился обмен;
- сколько сущностей создано/обновлено/пропущено;
- какие ошибки пришли;
- какой внешний GUID вызвал проблему.

Без журнала обмена интеграция с 1С быстро станет неотлаживаемой.

## Что добавить заранее

Без усложнения текущего MVP стоит заранее держать в документах и будущих миграциях такие правила:

1. Не добавлять цену и остаток как постоянную бизнес-истину в `products`.
2. Следующий каталоговый шаг делать через `product_variants`.
3. Все импортируемые сущности должны иметь связь с внешним GUID через integration mapping.
4. Цены проектировать как отдельный регистр.
5. Остатки проектировать как отдельный регистр по складам.
6. Спецификации оставить как будущий контур, не реализовывать в первом CRUD.
7. Массовые импорты 1С делать через DBAL/bulk операции и staging, а не через медленный ORM-цикл по одной записи.

## Простое объяснение

`Product` - это карточка номенклатуры. `ProductVariant` - то, что реально продается. `Price` - запись регистра цены. `InventoryLevel` - запись регистра остатка на складе. 1С приносит свои GUID, а ShopsBox связывает их со своими внутренними UUID через таблицу внешних идентификаторов.

Так мы не копируем 1С целиком, но строим каталог так, чтобы 1С-интеграция была естественной, а не пришитой сбоку.
