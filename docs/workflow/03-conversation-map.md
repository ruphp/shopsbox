# Карта рабочих бесед

Документ нужен, чтобы не смешивать все вопросы ShopsBox в одном длинном чате. Каждая беседа должна иметь понятную роль, а важные решения после обсуждения должны переноситься в документацию или задачи GitHub.

## Беседа 1. Управление проектом и бэклог

Для чего:

- задачи GitHub;
- доска проекта;
- этапы;
- приоритеты;
- разбор "что дальше";
- перевод карточек между статусами.

Когда писать сюда:

- нужно создать или уточнить задачу;
- нужно понять текущий статус проекта;
- нужно решить, что брать в работу;
- нужно разложить большой кусок на этапы.

Главное правило: после решения обновлять задачи, доску или `docs/workflow`.

## Беседа 2. ТЗ и архитектура

Для чего:

- техническое задание;
- карта страниц;
- доменная модель;
- роли и права;
- multi-tenancy;
- лимиты, тарифы и учет ресурсов;
- решения, которые влияют на будущий код.

Когда писать сюда:

- нужно обсудить "как правильно сделать";
- нужно сравнить варианты;
- нужно зафиксировать архитектурное решение;
- нужно подготовить план перед разработкой.

Главное правило: крупные решения фиксировать в `docs/tz` или `docs/architecture`.

## Беседа 3. Текущая разработка

Для чего:

- реализация текущей задачи;
- Symfony;
- миграции;
- сущности;
- контроллеры;
- use case;
- тесты;
- локальная проверка.

Когда писать сюда:

- задача уже выбрана и стоит в статусе `В работе`;
- нужно писать код;
- нужно чинить ошибку;
- нужно подготовить запрос на слияние.

Главное правило: перед новой фичей должна быть задача GitHub. Для отдельной фичи использовать отдельную ветку.

## Беседа 4. Инфраструктура и локальный контур

Для чего:

- Docker;
- PostgreSQL;
- Redis;
- MinIO;
- cron / scheduler;
- бэкапы;
- VDS/VPS-план;
- будущий CDN;
- наблюдаемость и healthchecks.

Когда писать сюда:

- нужно поднять или изменить локальный контур;
- нужно думать про масштабирование;
- нужно обсудить, за что будет платить проект;
- нужно подготовить production-план.

Главное правило: все повторяемые операции заводить через `make`.

## Беседа 5. Продукт, интерфейсы и тексты

Для чего:

- страницы админки;
- страницы витрины;
- пользовательские сценарии;
- тексты интерфейса;
- Bootstrap/Twig;
- будущие HTML-прототипы.

Когда писать сюда:

- нужно обсудить, как пользователь будет проходить сценарий;
- нужно составить карту страниц;
- нужно написать тексты;
- нужно подготовить UI без ухода в код backend.

Главное правило: сначала сценарий и структура, потом верстка и код.

## Как начинать новую беседу

В начале новой беседы стоит написать:

```text
Проект ShopsBox. Роль беседы: <название роли>.
Работаем по AGENTS.md. Текущий репозиторий: D:\codex\shopsbox.
Сначала посмотри CONTEXT.md, AGENTS.md и актуальный документ статуса.
```

Если беседа про реализацию, добавить:

```text
Текущая задача GitHub: #<номер>.
Цель: <коротко что делаем>.
```

## Что не держать только в чате

- архитектурные решения;
- список страниц;
- правила проекта;
- пароли демо-пользователей;
- план инфраструктуры;
- задачи и критерии приемки.

Все это должно попадать в `docs/`, `CONTEXT.md`, `AGENTS.md` или GitHub Issues.
