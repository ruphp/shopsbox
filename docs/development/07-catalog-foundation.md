# Catalog foundation

Документ фиксирует рабочее решение для задачи `#12 Основа каталога: товары и категории`.

## Цель

Создать минимальный модуль `Catalog` для товаров и категорий.

Это первый реальный бизнес-модуль ShopsBox после foundation-этапа. Он должен опираться на уже созданные границы `Tenant` и `Store`, но не тянуть в себя изображения, остатки, скидки, варианты товара, SEO, админский CRUD или витрину.

## Структура модуля

Фактическая структура первого шага:

```text
backend/src/Catalog/
  Domain/
  Application/
    Dto/
    Contracts/
    UseCase/
  Infrastructure/
    Persistence/
      Doctrine/
        Entity/
        Repository/
        Fixtures/
  Presentation/
```

`Domain` уже нужен, потому что у товара есть бизнес-значимый статус:

```text
draft
active
archived
```

На этом шаге статус представлен как `ProductStatus`. Сложные переходы состояний пока не добавляем: нет use case публикации/архивации, нет админского CRUD и нет витрины.

## Таблицы

### categories

Минимальная таблица категорий магазина.

Поля:

- `id`;
- `tenant_id`;
- `store_id`;
- `name`;
- `slug`;
- `created_at`;
- `updated_at`.

Уникальность:

- `store_id + slug`.

Категории пока плоские. Иерархию, сортировку, скрытие категории и SEO не добавляем до отдельной задачи.

### products

Минимальная таблица товаров магазина.

Поля:

- `id`;
- `tenant_id`;
- `store_id`;
- `category_id`, nullable;
- `name`;
- `slug`;
- `description`, nullable;
- `status`;
- `created_at`;
- `updated_at`.

Уникальность:

- `store_id + slug`.

Статусы:

- `draft` - товар создан, но не должен считаться опубликованным;
- `active` - товар можно показывать в будущей витрине;
- `archived` - товар убран из активного каталога без физического удаления.

## Границы задачи

Делаем:

- структуру модуля `Catalog`;
- Doctrine entities `Category` и `Product`;
- Doctrine repositories `DoctrineCategoryRepository` и `DoctrineProductRepository`;
- миграцию для `categories` и `products`;
- tenant/store boundary через внешние ключи и индексы;
- статус товара как доменное понятие.

Не делаем сейчас:

- изображения товара;
- загрузку файлов;
- остатки;
- скидки;
- варианты товара;
- SEO;
- сложные атрибуты;
- админский CRUD;
- витрину;
- модуль `Order`;
- модуль `Billing`;
- модуль `Integration` или `OneC`.

## Тестовое решение

На этом шаге unit-тесты для статусов товара не добавляются, потому что статус пока представлен нативным PHP enum без собственных правил переходов.

Тестировать сам факт, что PHP enum содержит `draft`, `active`, `archived`, не очень полезно: это будет проверка языка, а не нашей бизнес-логики.

Unit-тесты понадобятся, когда появится поведение:

- можно ли опубликовать товар из `draft`;
- можно ли вернуть `archived` товар в `active`;
- какие товары доступны для витрины;
- какие статусы разрешены для конкретного use case.

Проверки для текущего шага:

- `make migrate`;
- `make backend-check`;
- `make test`.

## Как дальше создавать миграции

В #12 миграция написана вручную: это дало полный контроль над именами таблиц, индексов, foreign keys и `onDelete`.

Для следующих изменений схемы используем более стандартный Doctrine-процесс:

```text
1. Изменить Doctrine entity mapping.
2. Запустить make migration-diff.
3. Проверить сгенерированную миграцию руками.
4. При необходимости поправить имена индексов/constraints.
5. Запустить make migrate.
```

`migration-diff` не заменяет ревью миграции. Doctrine генерирует заготовку, а разработчик проверяет, что она не удаляет лишнее, не создает странные индексы и правильно отражает tenant/store boundary.

## Проверки текущей реализации

- `make migrate` - успешно, применена миграция `DoctrineMigrations\Version20260418130000`.
- `make backend-check` - успешно, Symfony container lint и Doctrine mapping проходят.
- `make test` - успешно, 11 tests / 32 assertions.

Перед первым успешным `make migrate` пришлось очистить сгенерированный dev-cache Symfony в `backend/var/cache/dev`: контейнер не смог удалить старый cache-каталог. Это не изменение кода и не часть миграции, а локальная очистка ignored runtime-файлов.
