# Модели размещения

Документ фиксирует варианты размещения ShopsBox. Важно: ShopsBox не обязан быть только SaaS, где все данные и фронт живут у нас. У проекта с самого начала есть стратегический вариант, где фронт, база или часть backend находятся на инфраструктуре клиента.

## Зачем это нужно

Разным клиентам нужен разный уровень контроля:

- маленькому магазину важнее быстро запуститься и не думать о серверах;
- зрелому клиенту может быть важно владеть базой, фронтом, доменом и инфраструктурой;
- агентству может быть важно обслуживать клиента на его серверах, но иметь удобную админку и регламент управления.

ShopsBox должен поддерживать путь роста: начать с managed store, а потом при необходимости перейти к Own Infra без переписывания продукта с нуля.

## Вариант 1: Managed Store

Основной сценарий для MVP.

```text
Покупатель
  -> витрина ShopsBox
  -> backend ShopsBox
  -> БД ShopsBox

Владелец магазина
  -> админка ShopsBox
  -> backend ShopsBox
  -> БД ShopsBox
```

Что размещает ShopsBox:

- backend;
- витрину;
- базу данных;
- файлы;
- бэкапы;
- SSL;
- технический мониторинг.

Плюсы:

- быстрее запустить;
- проще поддерживать;
- проще делать обновления;
- лучше для первых клиентов и MVP.

Минусы:

- клиент меньше контролирует инфраструктуру;
- выше ответственность ShopsBox за доступность и бэкапы;
- нужно очень аккуратно держать tenant isolation.

Правило для платежей:

- поддомен ShopsBox подходит для демо, пилота, каталога и тестовой оплаты;
- боевой эквайринг на поддомене ShopsBox не является базовым сценарием;
- production-платежи должны идти через домен или поддомен клиента, merchant/терминал клиента, реквизиты клиента-продавца и его онлайн-кассу;
- ShopsBox не должен становиться фактическим получателем денег клиента без отдельной юридической, бухгалтерской и платежной модели.

## Вариант 2: Own Infra Light

Клиент размещает публичную витрину у себя, а ShopsBox остается админкой и core backend.

```text
Покупатель
  -> фронт клиента
  -> API ShopsBox
  -> БД ShopsBox

Владелец магазина
  -> админка ShopsBox
  -> API ShopsBox
  -> БД ShopsBox
```

Что размещает клиент:

- storefront/frontend;
- свой домен;
- CDN/статику при необходимости.

Что размещает ShopsBox:

- админку;
- backend API;
- БД;
- бэкапы;
- операционный контур.

Когда подходит:

- клиент хочет кастомную витрину;
- клиенту важно контролировать внешний frontend;
- backend и данные пока можно оставить в ShopsBox.

Риски:

- нужен стабильный Storefront API;
- нужно версионирование API;
- нужно объяснить клиенту границу ответственности.

## Вариант 3: Own Infra Data

Клиент размещает базу и, возможно, backend-сервис у себя. ShopsBox управляет магазином через защищенный agent/API.

```text
Покупатель
  -> витрина клиента или ShopsBox
  -> backend/agent клиента
  -> БД клиента

Владелец магазина
  -> админка ShopsBox
  -> platform API ShopsBox
  -> защищенный agent/API клиента
  -> БД клиента
```

Что размещает клиент:

- базу данных;
- agent/API;
- возможно backend магазина;
- возможно витрину;
- домен и часть файлов.

Что размещает ShopsBox:

- SaaS-админку;
- platform API;
- регистр агентов;
- конфигурацию подключения;
- аудит команд;
- обновления agent/API.

Ключевое правило:

> ShopsBox не должен ходить напрямую в базу клиента как основной механизм. Управление идет через защищенный agent/API на стороне клиента.

Когда подходит:

- клиенту важно владеть данными;
- есть требования безопасности;
- есть внутренняя инфраструктура;
- нужен контроль над базой и бэкапами;
- клиент готов платить за более сложную поддержку.

Риски:

- сложнее диагностика;
- сложнее обновления;
- нужно версионирование agent/API;
- нужен регламент безопасности;
- нужны подписи запросов, rotate secrets и аудит команд.

## Вариант 4: Own Infra Full

Клиент размещает фронт, backend и БД у себя. ShopsBox остается control plane: админка, управление, мониторинг, обновления и поддержка через agent/API.

```text
Покупатель
  -> фронт клиента
  -> backend клиента
  -> БД клиента

Владелец магазина
  -> админка ShopsBox
  -> platform API ShopsBox
  -> agent/API клиента
  -> backend/БД клиента
```

Что размещает клиент:

- storefront;
- backend;
- database;
- files;
- backups;
- runtime;
- домен и SSL.

Что дает ShopsBox:

- SaaS-админку;
- agent/API;
- обновления agent/API;
- мониторинг доступности agent;
- журнал команд;
- помощь с внедрением;
- регламент поддержки.

Когда подходит:

- enterprise/custom клиент;
- агентство или зрелый бизнес;
- есть своя инфраструктура;
- нужны требования владения данными;
- клиент готов к отдельному договору и регламенту.

Почему это не первый MVP:

- нужна зрелая API-модель;
- нужен агент;
- нужны безопасность и аудит;
- нужно тестировать обновления;
- нужна документация для клиента;
- поддержка такого режима дороже.

## Вариант 5: Self-hosted Licensed

Клиент получает ShopsBox как пустой Docker-дистрибутив и разворачивает продукт у себя по лицензии. Коробка продается целиком, а демо-данные переносятся только через явный импорт.

```text
Покупатель
  -> домен клиента
  -> ShopsBox instance клиента
  -> БД клиента или БД из дистрибутива

Владелец магазина
  -> админка на домене клиента
  -> ShopsBox instance клиента
  -> license check / updates через ShopsBox
```

Что размещает клиент:

- runtime;
- backend;
- storefront;
- database или подключение к своей БД;
- files;
- backups;
- SSL;
- monitoring.

Что дает ShopsBox:

- пустой Docker image / Docker Compose bundle;
- инструкцию установки;
- миграции и обновления;
- license file или license key;
- доступ к обновлениям в рамках лицензии;
- функциональность коробочной версии без деления на платные модули;
- внедрение и поддержку по отдельному договору.

Ключевые правила:

- self-hosted поставка не должна требовать постоянной связи с ShopsBox для работы магазина;
- отсутствие связи с license server не должно сразу останавливать продажи;
- без действующей лицензии можно ограничивать обновления, поддержку и увеличение лимитов;
- лицензия должна привязываться к production-домену, instance id и лимиту разрешенных активаций;
- один ключ не должен активировать несколько production-доменов без расширения лицензии;
- Docker image нельзя считать надежной защитой кода: клиент технически может его разобрать или изменить;
- защита строится на лицензии, подписи, договоре, обновлениях, закрытом registry и поддержке только неподмененных версий.

Подробная модель описана отдельно: [Self-hosted licensed поставка](08-self-hosted-licensed-delivery.md).

## Гибридный вариант

Можно комбинировать:

- фронт у клиента, backend и БД у ShopsBox;
- фронт и БД у клиента, админка и control plane у ShopsBox;
- все у клиента, ShopsBox только управляет через agent/API;
- коробочная self-hosted поставка через Docker и лицензию;
- отдельный инстанс managed store для клиента с повышенными требованиями.

Главное правило: у каждого варианта должна быть понятная граница ответственности.

## Коммерческая логика

Managed Store дешевле и проще:

- меньше внедрения;
- меньше переменных;
- больше автоматизации.

Own Infra и Self-hosted Licensed дороже:

- больше настройки;
- больше диагностики;
- выше требования к безопасности;
- нужно поддерживать agent/API;
- сложнее обновления;
- больше консультаций.

Поэтому Own Infra и Self-hosted Licensed не должны продаваться как “то же самое, только на ваших серверах”. Это отдельный тариф/проектная услуга с другими границами ответственности.

Границы ответственности по нагрузке и поддержке описаны отдельно: [Операционная ответственность и нагрузки](04-operational-responsibility-and-loads.md). Короткое правило: ShopsBox строго отвечает за админку/control plane. За storefront, backend и БД ShopsBox отвечает только в managed-контуре или отдельном договоре. Высокая нагрузка, выделенный SLA и отдельная отказоустойчивость продаются отдельным managed-контуром или Own Infra.

Инфраструктурная эволюция описана отдельно: [Инфраструктурная модель и масштабирование](07-infrastructure-scaling-model.md). Короткое правило: MVP начинается с shared managed-контура через Docker Compose; поддомены могут идти в общий backend; крупные клиенты получают отдельный runtime/dedicated contour; Kubernetes нужен позже, когда появится реальная операционная необходимость.

## Что заложить в MVP уже сейчас

Даже если Own Infra не реализуется первым, в MVP нужно не закрыть себе дорогу:

- проектировать API-first;
- не смешивать админку, витрину и backend-сценарии;
- держать tenant/store boundaries;
- не привязывать доменную логику к конкретной витрине;
- логировать важные действия;
- не делать прямой доступ к БД клиента базовым сценарием;
- выделить agent endpoints в API draft;
- описать security model для agent позже.

## Порядок реализации

1. Managed Store MVP.
2. Storefront API, чтобы можно было вынести фронт.
3. Own Infra Light: фронт клиента поверх API ShopsBox.
4. Agent/API прототип для Own Infra Data.
5. Own Infra Full только после стабильного API, аудита и регламента поддержки.
6. Self-hosted Licensed только после стабильного Docker-дистрибутива, миграций, документации обновлений и модели лицензирования.

Отдельный сценарий продаж и внедрения: сначала поднять demo/pilot store на поддомене ShopsBox, затем перенести production на выбранную модель размещения. Для production-платежей поддомен ShopsBox не является базовым вариантом: клиентский эквайринг должен подключаться к домену/поддомену клиента и реквизитам клиента-продавца. Сценарий описан в [Жизненном цикле магазина](05-store-lifecycle-demo-to-production.md).
