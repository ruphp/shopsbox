# Page builder витрины

Issue #29 фиксирует план будущего page builder-а. Это не реализация drag-and-drop, а граница модели, чтобы настройки витрины не превратились в неподдерживаемую кашу.

## Цель

Дать владельцу магазина управляемую витрину уровня простого конструктора:

- секции;
- блоки внутри секций;
- порядок;
- настройки;
- preview;
- переносимость шаблонов между магазинами.

## Что уже есть

Сейчас в `stores.theme_settings` лежит простой MVP-набор:

- цветовой пресет;
- hero title/text;
- включенные базовые секции.

Это нормальный первый слой. Его не надо растягивать до полноценного builder-а.

## Будущая модель

Минимальная модель builder-а:

- `storefront_pages` - страницы витрины магазина;
- `storefront_sections` - секции страницы;
- `storefront_blocks` - блоки внутри секций;
- `storefront_templates` - переносимые шаблоны;
- `storefront_page_versions` - черновик/опубликованная версия.

Для MVP можно начать с одной страницы `home`, но модель не должна закрывать путь к категориям, лендингам и промо-страницам.

## Типы секций

Первый набор:

- hero;
- featured products;
- category grid;
- product collection;
- text/image;
- contacts;
- custom HTML snippet только после отдельного решения по безопасности.

Каждый тип секции должен иметь схему настроек. Нельзя хранить произвольную мешанину без валидации.

## Формат хранения

Подход:

- порядок секций хранится явно;
- настройки секции хранятся JSON-структурой;
- тип секции определяет допустимые поля JSON;
- published version отделена от draft version.

Пример логики:

- владелец меняет draft;
- preview читает draft;
- публичная витрина читает только published;
- publish переносит draft в published snapshot.

## Backend/Frontend граница

Backend:

- хранит страницы, секции, блоки и версии;
- валидирует типы секций;
- проверяет tenant/store boundary;
- отдает read model для preview и public storefront.

Frontend:

- drag-and-drop порядок;
- редактор настроек секции;
- preview состояния;
- без прямой записи в базу.

## Preview

Preview должен быть отдельным route в кабинете владельца:

- доступ только авторизованному владельцу магазина;
- читает draft;
- не индексируется;
- не виден публичным посетителям.

Публичная витрина не должна читать черновик.

## Переносимость шаблонов

Шаблон должен быть независим от конкретных product/category UUID.

Для переносимости:

- секция может ссылаться на semantic slots: `featured`, `new`, `sale`;
- конкретные товары выбираются настройкой магазина;
- импорт шаблона не должен ломаться, если в магазине нет таких товаров.

## Что делать первым

Первая реализация после #29:

1. Вынести home layout из `stores.theme_settings` в отдельную draft/published структуру.
2. Добавить список секций с порядком.
3. Добавить preview route.
4. Добавить publish action.
5. Оставить drag-and-drop UI простым: порядок секций через кнопки вверх/вниз или минимальный sortable.

## Что не делать сразу

- произвольный HTML без sandbox;
- marketplace шаблонов;
- визуальный редактор каждого CSS-свойства;
- сложные animation settings;
- A/B testing;
- версионирование как в CMS enterprise-уровня.

## Проверки и тестовое покрытие

Для этого issue новые тесты не нужны: это архитектурный документ без production-кода.

Когда начнется реализация, нужны:

- unit-тесты схем секций;
- integration-тесты tenant/store boundary;
- functional-тесты preview/publish;
- smoke-check публичной витрины, что она читает published, а не draft.
