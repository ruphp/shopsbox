# Self-hosted licensed поставка

## Смысл модели

ShopsBox должен рассматривать не только SaaS/managed-размещение, но и поставку продукта клиенту в виде Docker-дистрибутива с лицензией.

Рабочее название модели: `Self-hosted Licensed`.

Клиент получает пустую коробочную версию:

- базовый Docker image или Docker Compose bundle без демо-данных клиента;
- инструкцию установки;
- возможность подключить свою БД или использовать БД из дистрибутива;
- файл лицензии или license key;
- обновления в рамках срока лицензии;
- функциональность коробочной версии без деления на платные модули;
- отдельный скрипт импорта демо-данных, если клиент переносит данные из демо-контура.

Это не первый MVP, но архитектура не должна закрывать такой путь.

## Чем отличается от Own Infra

`Own Infra` в текущем смысле - это сценарий, где ShopsBox остается control plane и управляет магазином через agent/API.

`Self-hosted Licensed` - это коробочная поставка: продукт работает у клиента автономно, а связь с ShopsBox нужна для лицензии, обновлений, поддержки, увеличения лимитов и, возможно, телеметрии.

## Базовый сценарий установки

1. Клиент покупает лицензию.
2. ShopsBox выдает пустой Docker-дистрибутив и инструкцию.
3. Клиент разворачивает продукт на своем сервере.
4. Клиент выбирает режим БД:
   - внешняя БД клиента;
   - БД в составе Docker Compose дистрибутива.
5. Клиент кладет license file или вводит license key.
6. Приложение проверяет лицензию, срок обновлений и лимиты.
7. Если нужно перенести демо, запускается отдельный импорт демо-данных.
8. Обновления поставляются через новые Docker images и миграции.

## Пустая коробка и функциональные модули

Коробочная поставка не должна собираться как индивидуальный image с данными конкретного клиента.

Базовый подход:

- один официальный image ядра ShopsBox;
- функциональные модули используются как архитектурное деление кода, а не как прайс-лист;
- license file определяет срок обновлений, домены/инстансы и лимиты;
- конфигурация клиента хранится в env/config файлах и БД;
- демо-данные переносятся отдельным экспортом/импортом.

Такой подход оставляет обновления проще: ядро можно обновлять отдельно от клиентских данных, а коммерцию держать на лицензии, поддержке, лимитах и работах по внедрению.

Демо-контур может содержать расширенные возможности, тестовые платежи, тестовые интеграции и пример каталога. В коробочную поставку они попадают только через явный импорт, если клиент решил переносить демо-настройки.

## Удаленная настройка через ShopsBox

Возможен отдельный режим внедрения: клиент в админке ShopsBox или в onboarding-форме указывает SSH-доступы, а ShopsBox помогает развернуть продукт на сервере клиента.

Это должно быть отдельной услугой, а не скрытым базовым механизмом.

Обязательные требования:

- явное согласие клиента;
- временные SSH-доступы или отдельный deploy-user;
- аудит действий;
- запрет хранить пароли в открытом виде;
- поддержка SSH keys;
- возможность удалить доступ после внедрения;
- понятная граница ответственности: сервер клиента остается ответственностью клиента, если другое не указано в договоре.

## Перенос с демо

Демо-магазин на поддомене ShopsBox должен быть переносим в self-hosted поставку только через отдельный импорт, а не через сборку индивидуального Docker image с данными клиента:

- tenant/store settings;
- каталог;
- страницы и настройки витрины;
- пользователи и роли;
- файлы, если клиент переносит storage;
- настройки платежей и доставки, если они поддержаны в коробке.

Перенос должен выполняться через экспорт/импорт или отдельный migration package, а не через ручное копирование БД без правил.

Импорт демо должен быть повторяемым и проверяемым:

- экспорт формирует manifest с версией ShopsBox, tenant/store, списком сущностей и файлов;
- импорт проверяет совместимость версий и нужной функциональности;
- секреты платежек, интеграций и SSH-доступы не переносятся как открытый текст;
- после импорта запускается healthcheck и отчет о перенесенных данных.

## Лицензия и лимиты

Лицензия должна описывать:

- срок действия;
- клиента или организацию;
- домены/инстансы, если это нужно;
- production domain;
- instance id установки;
- количество разрешенных production/staging/dev активаций;
- лимиты магазинов, пользователей, товаров или заказов;
- право на обновления;
- уровень поддержки;
- режим проверки: online, offline или grace period.

Через админку ShopsBox в будущем можно управлять:

- продлением срока;
- увеличением лимитов;
- историей оплат;
- доступом к обновлениям;
- выпуском нового license file.

## Защита от использования одной лицензии на нескольких доменах

Для self-hosted поставки базовая модель лицензирования должна привязывать лицензию не только к клиенту, но и к установке.

Минимальные поля:

- `customer_id`;
- `license_key`;
- `production_domains`;
- `staging_domains`;
- `instance_id`;
- `allowed_production_activations`;
- `allowed_staging_activations`;
- `modules`;
- `limits`;
- `expires_at`;
- `updates_until`.

При первой активации установленный ShopsBox генерирует `instance_id` и отправляет его на license server вместе с доменом, версией продукта и license key. License server проверяет лимит активаций и возвращает подписанный local license file.

Базовое правило тарифа:

- 1 production domain;
- 1 production instance;
- 1 staging instance;
- dev/test режимы только для разработки и проверки обновлений.

Если тот же ключ пытаются активировать на втором production-домене или втором production-инстансе, активация не должна проходить без расширения лицензии.

Смена сервера или домена должна быть нормальным сценарием:

- клиент инициирует перенос лицензии в кабинете ShopsBox или через поддержку;
- старый `instance_id` деактивируется;
- новый `instance_id` активируется;
- выпускается новый signed license file.

Если нарушение обнаружено после активации, магазин не должен выключаться мгновенно. Безопасная реакция:

- показать предупреждение владельцу;
- запретить обновления;
- запретить увеличение лимитов;
- ограничить поддержку до решения вопроса с лицензией;
- оставить продажи работающими, если договор не требует другого.

## Проверка лицензии

Базовый принцип: отсутствие связи с ShopsBox не должно сразу ломать работающий магазин клиента.

Возможные режимы:

- `online check` - продукт периодически связывается с license server ShopsBox;
- `offline license file` - подписанный файл лицензии работает без постоянной связи;
- `grace period` - если связи нет, магазин продолжает работать ограниченное время;
- `updates only` - при проблеме с лицензией магазин продолжает работать, но обновления, расширенная поддержка и увеличение лимитов недоступны.

Для доверия клиентов безопаснее начинать с подхода: магазин продолжает работать, но без действующей лицензии нельзя получать обновления, расширенную поддержку и увеличение лимитов. Жесткое отключение магазина из-за временной потери связи с license server использовать нельзя без отдельного договора.

## Защита Docker image

Нельзя считать Docker image надежной защитой кода. Клиент с доступом к серверу технически может:

- извлечь содержимое image;
- посмотреть PHP-код;
- изменить файлы в контейнере или volume;
- попытаться подменить license check.

Поэтому защиту строим не на иллюзии полной закрытости image, а на сочетании:

- подписанного license file;
- проверки подписи лицензии;
- юридического договора;
- ограниченного доступа к обновлениям;
- закрытого registry для production images;
- поддержки только неподмененных версий;
- ценности SaaS/обновлений/поддержки, которую сложно заменить простым копированием кода.

Обфускация может усложнить копирование, но не должна быть главным механизмом защиты.

## Что не делать в MVP

- Не реализовывать license server.
- Не делать удаленную установку по SSH.
- Не делать модульную покупку функций.
- Не обещать полноценную коробочную поставку первым клиентам.
- Не строить безопасность на предположении, что Docker image нельзя разобрать.

## Что заложить заранее

- Runtime через Docker Compose.
- Конфигурация через env и файлы, а не через хардкод.
- Миграции БД как обязательный путь обновления.
- Отделение доменной логики от SaaS-only сценариев.
- Возможность работать с внешней БД.
- Документированный путь обновления.
- Явная модель тарифных лимитов в будущем.
