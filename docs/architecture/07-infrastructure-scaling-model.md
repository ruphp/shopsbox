# Инфраструктурная модель и масштабирование

Документ отвечает на вопрос: как профессионально размещать ShopsBox, где арендовать ресурсы, как работают поддомены, общая админка, storefront клиентов и когда нужен Kubernetes.

## Главная мысль

На MVP не нужно начинать с Kubernetes. Профессиональный путь обычно такой:

1. Простой managed/shared контур.
2. Разделение приложения, БД, файлов и статики.
3. Учет нагрузки по tenants/stores.
4. Горизонтальное масштабирование stateless backend.
5. Выделенные контуры для крупных клиентов.
6. Kubernetes только когда Docker Compose/простые VM уже мешают управлять ростом.

## Что арендуется

На старте обычно арендуются не "железки" в смысле покупки серверов, а инфраструктурные ресурсы:

- VM/VPS или cloud instances для backend/web/worker;
- managed PostgreSQL или отдельная VM под PostgreSQL;
- object storage для файлов и изображений;
- CDN для публичной статики и изображений;
- backup storage;
- Redis/cache, если нужен;
- monitoring/logging;
- домены, DNS, SSL.

Если хостинг простой, часть этого может жить на одной VM. Если провайдер зрелый, лучше выносить БД, файлы и CDN в отдельные managed-сервисы.

## Базовая схема разработки

Первый этап - локальная разработка в Docker Compose. Мы не деплоим ShopsBox на VDS/VPS сразу, а моделируем будущий серверный контур локально:

```text
local machine
  -> Docker Compose
      -> shopsbox_web / shopsbox_backend
      -> shopsbox_postgres
      -> shopsbox_redis
      -> shopsbox_minio / s3-compatible storage
      -> shopsbox_worker later
      -> shopsbox_scheduler later
```

Смысл: локально повторить будущие зависимости так, будто потом это может уехать на VDS/VPS или cloud VM, но не делать production-деплой раньше времени.

CDN на этом этапе не нужен. Для Twig + Bootstrap MVP достаточно обычной отдачи статики в локальном/простом серверном контуре. CDN появится позже, если usage metrics покажут нагрузку на изображения и публичную витрину.

## Базовая production-pilot схема

Когда появится необходимость показать проект реальному клиенту, стартовая серверная схема может быть такой:

```text
DNS
  -> VPS/VDS or cloud VM / reverse proxy
  -> Docker Compose
      -> Symfony backend / web runtime
      -> PostgreSQL
      -> Redis if needed
      -> MinIO/local storage or external S3-compatible storage
      -> worker if needed
      -> cron/scheduler runner if needed
```

Это простой старт: один VPS/VDS или cloud VM, БД рядом, S3-compatible storage по мере готовности и CDN позже, когда появится реальная нагрузка на витрину/изображения. Но код нельзя писать так, будто эта машина навсегда останется единственной.

Более зрелая схема после первого роста:

```text
DNS
  -> reverse proxy / load balancer
  -> Symfony backend / web runtime
  -> PostgreSQL
  -> S3-compatible object storage / local file storage на старте

CDN, если подключен
  -> static assets / product images

Redis
  -> cache / sessions / locks / queue transport later

Cron/scheduler
  -> регулярные задачи через один управляемый runner
```

На первом шаге допустим Docker Compose только локально. Позже тот же подход можно перенести на одну VM/VDS для production-пилота.

Локальный Docker должен по возможности повторять будущие внешние зависимости, чтобы не писать код "под одну папку на диске":

```text
web/backend
postgres
redis
minio / s3-compatible storage
worker later
cron/scheduler runner later
```

`minio` нужен как локальная S3-compatible замена будущему object storage. Даже если в первом production-пилоте файлы временно лежат на local volume, код должен работать через один storage interface.

Но даже в такой простой схеме код должен готовиться к будущему росту:

- не хранить пользовательские файлы внутри контейнера приложения;
- работать с файлами через storage-абстракцию, чтобы позже перейти с local volume на S3-compatible/object storage;
- не рассчитывать на локальную сессию в памяти одного процесса;
- не делать cron-задачи руками как набор случайных записей на VPS: регулярные задачи должны идти через Symfony console/Scheduler и один управляемый runner;
- отделять БД от файлов;
- не прошивать локальные пути VPS в бизнес-логике;
- не завязывать генерацию URL изображений на конкретный домен, если позже будет CDN или S3 public endpoint;
- логировать tenant/store в важных событиях;
- делать healthcheck endpoints;
- держать backend stateless там, где это возможно.

## Как работают домены и поддомены

Обычно маршрутизация идет через reverse proxy/load balancer:

```text
admin.shopsbox.ru
  -> ShopsBox admin/control plane

client-demo.shopsbox.ru
client-pilot.shopsbox.ru
client.shopsbox.ru
  -> storefront renderer / storefront route

api.shopsbox.ru
  -> platform API / storefront API

custom-client-domain.ru
  -> storefront конкретного магазина
```

Приложение определяет магазин по:

- домену;
- поддомену;
- `store_id` в маршруте/API;
- привязке домена в таблице `stores` или отдельной таблице доменов позже.

Важно: поддомены не означают отдельные серверы. Много поддоменов могут идти в один общий backend, если tenant isolation сделан правильно.

## Общая админка и витрины клиентов

На MVP можно иметь один Symfony backend:

```text
Админка ShopsBox
  -> тот же backend
  -> admin routes/API

Витрина клиента
  -> тот же backend
  -> storefront routes/API

Публичное API
  -> тот же backend
  -> API routes
```

Это нормально для старта, если внутри есть четкое разделение:

- admin/control plane;
- storefront;
- platform API;
- tenant/store boundary;
- роли и права;
- логирование действий.

Позже можно разделить:

- админку и storefront на разные frontend-приложения;
- storefront renderer в отдельный сервис;
- API в отдельный контур;
- крупных клиентов на dedicated instance.

## Горизонтальное масштабирование

Горизонтальное масштабирование означает: вместо одной копии backend запускается несколько одинаковых копий за load balancer.

Пример:

```text
load balancer
  -> backend-1
  -> backend-2
  -> backend-3

backend-* -> PostgreSQL
backend-* -> Redis
backend-* -> object storage
```

Для этого backend должен быть stateless:

- сессии не должны жить только в памяти одного backend;
- файлы не должны сохраняться только на локальный диск одного контейнера;
- фоновые задачи должны идти через очередь;
- cron/worker задачи не должны случайно запускаться в трех копиях одновременно без блокировок;
- конфигурация должна приходить из env/secrets, а не из ручных файлов на сервере.

## Масштабирование по поддоменам

Масштабирование не обязательно делается "по поддоменам". Есть несколько вариантов:

### Shared backend для всех поддоменов

```text
*.shopsbox.ru -> общий backend -> shared DB
```

Это стартовый вариант для MVP. Дешевле, проще, быстрее.

Риск: один тяжелый клиент может влиять на соседей, поэтому нужны лимиты и usage metrics.

### Отдельный storefront/runtime для крупного клиента

```text
client.shopsbox.ru -> dedicated backend/client runtime
admin.shopsbox.ru -> общий control plane
```

Подходит, когда клиент вырос по трафику, но админка и управление остаются общими.

### Полный dedicated managed

```text
client-domain.ru -> dedicated frontend/backend/db
admin.shopsbox.ru -> общий control plane или отдельный admin-контур по договору
```

Подходит для высокого трафика, SLA, особых требований безопасности.

## Где здесь Kubernetes

Kubernetes полезен, когда есть реальная операционная боль:

- много сервисов и окружений;
- нужно быстро масштабировать копии backend/worker;
- нужны rolling updates;
- нужны resource limits/requests;
- нужно разделять клиентов по namespaces;
- есть несколько dedicated-контуров;
- нужно автоматизировать деплой и восстановление;
- есть человек или команда, которая понимает эксплуатацию Kubernetes.

Kubernetes не нужен как первый шаг, если:

- нет стабильного MVP;
- нет нагрузочных тестов;
- нет понятного CI/CD;
- нет регламента мониторинга и бэкапов;
- один Docker Compose контур еще покрывает задачу.

Правило для ShopsBox:

> Docker Compose - основной runtime-контур MVP. Kubernetes - будущий путь, когда появится реальная нагрузка, несколько контуров и необходимость управлять ими как платформой.

## Профессиональная эволюция ShopsBox

### Шаг 1: Local Docker contour

- локальная машина разработчика;
- Docker Compose;
- Symfony backend;
- PostgreSQL;
- Redis;
- MinIO/S3-compatible storage;
- worker позже;
- cron/scheduler runner позже;
- make-команды как единственный вход.
- Docker Compose project, containers, networks and volumes с префиксом `shopsbox_`.

Цель: разработать приложение и проверить архитектурные решения без внешнего деплоя.

### Шаг 2: Production pilot contour

- один VPS/VDS или cloud VM;
- Docker Compose;
- Symfony backend;
- PostgreSQL на той же VM допустим для старта, но с планом выноса;
- файлы можно начать с local volume, но только через storage-абстракцию;
- S3-compatible storage можно подключить сразу или повторять локально через MinIO, если ожидаются изображения товаров и важна простая миграция между серверами;
- CDN не критичен для первого MVP на Twig + Bootstrap; его можно подключить позже для изображений и публичной статики, когда появится трафик;
- Redis можно подключить сразу, если нужны cache, sessions, locks или transport для очередей;
- cron/scheduler runner позже нужен для регулярных задач: бэкапы, очистка временных файлов, сбор usage metrics, healthchecks;
- production-бэкапы не обязательны на самом раннем dev-этапе, но обязательны перед реальными клиентами;
- домены и SSL;
- ручной мониторинг плюс простые healthchecks.

### Шаг 3: Managed shared contour

- backend/web отдельно от PostgreSQL;
- object storage для файлов;
- CDN для изображений и публичной статики, если usage metrics показывают смысл;
- Redis для cache/session/locks/queue transport;
- worker для фоновых задач;
- отдельный cron/scheduler runner;
- централизованные логи;
- usage metrics по tenant/store.

### Шаг 4: Horizontal scale

- несколько backend replicas;
- load balancer;
- очередь для фоновых задач;
- managed PostgreSQL или отдельная оптимизированная БД;
- cache;
- CDN;
- лимиты и алерты по клиентам.

### Шаг 5: Dedicated Managed

- отдельный runtime для крупного клиента;
- возможно отдельная БД/schema;
- отдельный регламент бэкапов;
- отдельные лимиты и SLA;
- общая админка/control plane может сохраняться.

### Шаг 6: Kubernetes/platform

- несколько окружений и клиентов;
- namespaces или отдельные clusters для крупных клиентов;
- Helm/GitOps/CI-CD;
- autoscaling там, где он реально нужен;
- централизованный monitoring/logging;
- policy/security controls.

## Триггеры расширения

Расширение инфраструктуры должно происходить не "потому что пора по-взрослому", а по понятным сигналам.

### Перейти от одной VM к более аккуратному shared contour

Сигналы:

- файлы и бэкапы начинают быстро расти;
- восстановление из бэкапа становится важным для реальных клиентов;
- локальный диск приложения становится риском;
- появляются первые клиенты с регулярными заказами;
- ручной просмотр логов уже неудобен.

Что делать:

- вынести файлы в object storage;
- настроить нормальные бэкапы БД и файлов;
- добавить Redis/cache, если он нужен;
- добавить worker для фоновых задач;
- добавить централизованные логи;
- начать собирать usage metrics по tenant/store.

## Бэкапы по этапам

На раннем этапе разработки:

- не поднимать сложный backup-сервис;
- не тратить время на production-grade restore policy;
- достаточно помнить о будущей модели `backups` и не хранить данные так, чтобы их нельзя было вынести;
- когда появится PostgreSQL, добавить make-команды для ручного dump/restore по необходимости.

Перед production-пилотом с реальными клиентами:

- настроить регулярный backup БД;
- настроить backup файлов или object storage bucket policy;
- описать срок хранения;
- проверить ручное восстановление хотя бы один раз;
- начать учитывать размер бэкапов по store/tenant.

После роста:

- автоматизировать scheduler-runner для backup/cleanup/usage metrics;
- разделить backup policy по тарифам;
- добавить алерты на неуспешный backup;
- продавать увеличенный срок хранения и дополнительные restore points как часть старших тарифов или add-on.

### Подключить CDN

Сигналы:

- растет трафик изображений и публичной витрины;
- магазин запускает рекламу и получает пики посещений;
- страницы с картинками грузятся медленно;
- статика начинает заметно стоить или нагружать backend;
- появляются клиенты из разных регионов.

CDN не является критичным стартовым требованием, потому что MVP-интерфейсы строятся на Twig + Bootstrap, без отдельного тяжелого React frontend. На старте важнее правильно отделить файлы, URL generation и storage, чтобы CDN можно было подключить без переписывания каталога и витрины.

Что делать:

- отдавать изображения и публичные assets через CDN;
- считать static egress и request count по доменам/магазинам;
- добавить лимиты статического трафика в тарифы;
- оставить admin/control plane отдельно от storefront traffic.

### Горизонтально масштабировать backend

Сигналы:

- backend CPU/RAM регулярно близки к лимиту;
- p95 latency растет в рабочее время;
- один backend становится single point of failure;
- фоновые задачи мешают HTTP-запросам;
- нужно обслуживать пики без ручного увеличения сервера.

Что делать:

- сделать backend stateless;
- вынести сессии/cache в Redis или другой общий слой;
- вынести файлы из контейнера;
- добавить load balancer;
- запустить несколько backend replicas;
- фоновые задачи вынести в worker;
- проверить блокировки для cron/worker задач.

### Выделить клиента в Dedicated Managed

Сигналы:

- один клиент стабильно создает большую долю API/DB/static нагрузки;
- рекламные пики клиента мешают соседним магазинам;
- нужны отдельные лимиты, SLA, бэкапы или безопасность;
- клиент готов платить за выделенный контур;
- клиенту нужны нестандартные интеграции или тяжелые импорты.

Что делать:

- выделить runtime для клиента;
- при необходимости выделить БД/schema;
- оставить общую админку/control plane, если это подходит договору;
- настроить отдельные бэкапы и мониторинг;
- зафиксировать отдельный тариф и регламент.

### Переходить к Kubernetes/platform

Сигналы:

- несколько shared/dedicated контуров уже трудно обслуживать вручную;
- нужны повторяемые деплои и rollback;
- нужны resource limits/requests для сервисов;
- нужна изоляция клиентов по namespaces или clusters;
- появляются отдельные staging/production окружения;
- есть CI/CD, мониторинг и человек, который понимает эксплуатацию Kubernetes.

Что делать:

- сначала описать production requirements;
- подготовить CI/CD;
- описать Helm/GitOps подход;
- начать с одного не критичного окружения;
- переносить контуры постепенно;
- не делать Kubernetes заменой архитектуры, лимитов и мониторинга.

## Что заложить уже в MVP, чтобы не переписывать потом

- `tenant_id` / `store_id` во всех бизнес-данных и метриках.
- Отдельную модель файлов, чтобы позже переехать на object storage.
- Локальный MinIO/S3-compatible storage в Docker как способ проверять storage-интеграцию без привязки к VPS.
- Отдельные настройки доменов и storefront.
- Stateless backend там, где это возможно.
- Очереди для фоновых задач как направление, даже если worker появится не в первый день.
- Cron/scheduler abstraction для регулярных задач, чтобы при нескольких backend replicas они не запускались в нескольких местах одновременно.
- Healthchecks.
- Логи с контекстом tenant/store.
- Usage metrics по storage/API/static traffic.
- Make-команды как единый вход для локального и серверного контура.
- Storage interface для файлов, даже если первая реализация сохраняет их локально.
- URL builder для публичных файлов, чтобы позже переключить домен/CDN без переписывания product/catalog кода.
- Конфигурацию окружений через env/secrets, а не через ручные пути конкретного VPS.

## Как объяснять клиенту

Простыми словами:

> На старте ваш магазин работает в managed-контуре ShopsBox. Малые магазины живут в общем надежном контуре с лимитами. Если магазин растет, мы не выключаем его, а переводим на старший тариф, добавляем CDN, выделяем ресурсы или переносим в Dedicated Managed. Общая админка может оставаться той же, но технический контур под витрину/backend/БД становится мощнее.
