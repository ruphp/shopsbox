# Архитектура

## Цели

- Дать клиентам простой интернет-магазин под ключ.
- Сохранить возможность отделить данные и фронт клиента от SaaS-админки.
- Не усложнять MVP Kubernetes и микросервисами раньше времени.
- Сразу держать код в форме, пригодной для роста: Clean Architecture, DDD, SOLID.

## Основной вариант на старт

Managed Store:

```text
Клиент / покупатель
  -> web/mobile storefront
  -> backend магазина
  -> база магазина

Владелец магазина
  -> SaaS-админка
  -> platform backend
  -> API магазина / internal service layer
```

На старте выбран модульный монолит: один Symfony backend, одна кодовая база и один runtime-контур, но с четким разделением доменов и модулей. Важно не смешивать бизнес-логику с контроллерами и ORM.

## Вариант для Own Infra

```text
SaaS-админка ShopsBox
  -> platform API
  -> защищенный agent/API на стороне клиента
  -> backend/БД/фронт клиента
```

Для Own Infra нельзя проектировать прямой доступ SaaS-админки к базе клиента как основной механизм. Безопаснее использовать API/agent, который находится в инфраструктуре клиента и сам решает, какие операции доступны.

Подробные варианты размещения описаны в [Моделях размещения](03-deployment-models.md): Managed Store, Own Infra Light, Own Infra Data, Own Infra Full и гибридные схемы.

## Backend

Стартовый стек:

- PHP.
- Symfony.
- PostgreSQL как базовый кандидат для основной БД.
- Doctrine Migrations для версионирования схемы БД.
- Doctrine ORM для обычных CRUD-сценариев и понятной интеграции с Symfony.
- Doctrine DBAL/native SQL для горячих запросов, отчетов, массовых операций, резервирования остатков и сложных выборок.
- Messenger для очередей и фоновых задач.
- API Platform или собственные контроллеры - решение принять после прототипа API.

## Persistence strategy

Doctrine Migrations не считается проблемой производительности приложения: миграции запускаются при изменении схемы БД, а не на каждом пользовательском запросе.

Потенциально тяжелой может быть Doctrine ORM, если использовать ее не по назначению: массовые импорты, bulk updates, сложные отчеты, частые пересчеты остатков. Поэтому стратегия такая:

- Для обычной админки, CRUD и доменных сущностей использовать Doctrine ORM.
- Для изменения схемы БД использовать Doctrine Migrations.
- Для сложных и быстрых запросов использовать Doctrine DBAL или native SQL внутри infrastructure/repository слоя.
- Не добавлять Cycle ORM или Active Record во второй стек на MVP, чтобы не усложнять проект и обучение Symfony.
- Если позже появится реальная нагрузка, оптимизировать конкретные hot paths: индексы, DBAL-запросы, batch processing, очереди, кэширование, отдельные read models.

Как объяснять:

> Doctrine ORM используется там, где удобна работа с сущностями. Для тяжелых запросов мы не заставляем ORM делать то, для чего он плохо подходит, а пишем отдельные DBAL/SQL-запросы в infrastructure-слое. Миграции нужны только для контроля изменений схемы БД.

## Границы доменов

Предварительные bounded contexts:

- Catalog: товары, категории, свойства, изображения.
- Pricing: цены, скидки, промокоды.
- Inventory: остатки, склады, резервы.
- Order: корзина, заказ, статусы, оплата, доставка.
- Customer: покупатели, адреса, история.
- Storefront: настройки витрины, темы, страницы.
- Tenant: клиент, магазин, тариф, лимиты.
- Billing: платежи клиента за SaaS/managed hosting.
- Integration: внешние сервисы оплаты, доставки, CRM, склад.
- Support/Ops: бэкапы, статус сервисов, обращения.

## Clean Architecture

Рекомендуемое разделение внутри backend:

- Domain: сущности, value objects, доменные сервисы, события, интерфейсы репозиториев.
- Application: use cases, команды, запросы, DTO в `Application/Dto`, контракты внешних действий в `Application/Contracts`, транзакционные сценарии. DTO может собираться в Presentation из формы или HTTP-запроса, но класс DTO принадлежит Application.
- Infrastructure: Doctrine, внешние API, файловое хранилище, очереди, почта.
- Presentation: HTTP controllers, forms, Twig/API output, search/view models, CLI commands, admin API, webhooks. DTO для сценариев по умолчанию не кладем в Presentation.

Подробные правила разработки на Symfony вынесены в [Правила разработки на Symfony](01-symfony-development-rules.md).

## Multi-tenant модель

На старте выбран базовый вариант для MVP:

```text
Shared app + shared DB + tenant_id в таблицах.
```

Почему так: это быстрее для первого Symfony MVP, проще для миграций и локальной разработки, и достаточно для ранней проверки продукта. В коде и схеме БД нельзя забывать tenant/store boundary: данные магазина должны фильтроваться по `tenant_id` или `store_id` на уровне application/infrastructure слоя.

Альтернативы остаются в дорожной карте:

- Shared app + отдельная DB/schema на магазин.
- Отдельный контейнер/инстанс на магазин для managed hosting.

Для клиентов с повышенными требованиями позже можно перейти к отдельной DB/schema или отдельному инстансу.

## Frontend web

Нужно принять отдельное решение:

- Symfony + Twig + Bootstrap для простого старта.
- Symfony API + SPA frontend для более гибкой админки в будущем.
- Отдельный storefront renderer для клиентских витрин.

Принятое решение для MVP: web-админку и первую витрину делать на Twig + Bootstrap. Интерактивность добавлять точечно через Stimulus или простой JavaScript.

React + TypeScript не берем в первый MVP, потому что это добавит второй большой стек и усложнит обучение Symfony. Его можно добавить позже для отдельных сложных экранов или новой версии админки.

API все равно проектируется аккуратно, чтобы потом переиспользовать backend для mobile/desktop и возможного SPA frontend.

## Kotlin Multiplatform

Kotlin Multiplatform подходит как стратегическая опция для:

- Android/iOS приложения владельца магазина.
- Android/iOS приложения покупателя.
- Общей бизнес-логики: сетевой слой, модели, валидации, сценарии.

Для Windows desktop нужно отдельно проверить практичность:

- Compose Multiplatform может подойти для desktop.
- Можно начать с web-админки и позже завернуть ее в desktop shell.

Рекомендация: не начинать MVP с полного KMP-комплекта. Сначала стабилизировать backend API и web-админку, затем делать mobile owner app с узким функционалом.

## Инфраструктура

Подробная схема инфраструктурной эволюции описана в [Инфраструктурной модели и масштабировании](07-infrastructure-scaling-model.md).

Старт:

- Docker Compose.
- Отдельные контейнеры для backend, web server, database, queue worker, cache.
- Бэкапы БД и файлов.
- Логи и healthchecks.

Позже:

- Kubernetes.
- Helm charts.
- Автоматизированные деплои.
- Горизонтальное масштабирование.
- Изоляция клиентов на уровне namespaces или отдельных кластеров при необходимости.

## Безопасность

Нужно заложить с начала:

- Разделение tenants.
- Роли и права.
- Журнал действий.
- 2FA для админки.
- Бэкапы и регулярное тестовое восстановление.
- Шифрование секретов.
- Ограничение доступа к agent/API.
- Webhook signatures.
- Rate limits.
