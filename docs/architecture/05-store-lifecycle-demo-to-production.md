# Жизненный цикл магазина: демо, пилот, production

Документ описывает сценарий: сначала быстро показать клиенту магазин на поддомене ShopsBox, а потом перенести production-контур на хостинг клиента или в отдельный managed-контур.

## Идея

ShopsBox может создавать наглядные демо-магазины на своих поддоменах:

```text
client-demo.shopsbox.ru
admin.shopsbox.ru
```

Клиент видит:

- витрину;
- товары;
- корзину;
- checkout;
- админку;
- технический статус.

После согласования клиент выбирает production-модель:

- остаться в managed-контуре ShopsBox;
- подключить свой домен к managed-контру ShopsBox;
- перенести storefront на свой хостинг;
- перенести storefront, backend и БД на свой хостинг;
- использовать рекомендованного хостинг-партнера.

## Этап 1: Demo Store

Назначение: быстро показать, как магазин будет выглядеть и работать.

Размещение:

```text
Поддомен ShopsBox -> витрина ShopsBox -> backend ShopsBox -> demo/test DB
Админка ShopsBox -> backend ShopsBox -> demo/test DB
```

Что можно делать:

- наполнить тестовый каталог;
- показать категории и карточку товара;
- показать корзину и checkout в тестовом режиме;
- показать админку владельца;
- собрать обратную связь.

Что нельзя обещать:

- production SLA;
- высокую нагрузку;
- реальные платежи без отдельной настройки;
- долгосрочное хранение данных без договора.

Коммерчески:

- может быть бесплатным коротким демо;
- может входить в оплату запуска;
- может быть платным прототипом для клиента, если требуется много настройки.

## Этап 2: Pilot Store

Назначение: проверить реальный сценарий клиента на ограниченном объеме.

Размещение:

- поддомен ShopsBox или временный домен клиента;
- отдельная pilot DB или явно помеченный tenant/store;
- тестовые или ограниченные production-данные.

Что проверяем:

- каталог;
- оформление заказа;
- роли сотрудников;
- ручные оплаты и доставки;
- импорт товаров;
- базовые бэкапы;
- технический статус.

Ограничение:

> Pilot не должен незаметно стать production без выбора тарифа, ответственности и модели размещения.

## Этап 3: Production Choice

Перед production клиент выбирает модель размещения.

### Вариант A: Managed Production

Клиент остается в ShopsBox managed.

```text
client-shop.ru -> витрина ShopsBox -> backend ShopsBox -> production DB ShopsBox
admin.shopsbox.ru -> backend ShopsBox -> production DB ShopsBox
```

ShopsBox отвечает за managed-контур в пределах тарифа.

### Вариант B: Own Frontend

Клиент размещает фронт у себя, но backend и БД остаются у ShopsBox.

```text
client-shop.ru -> frontend клиента -> Storefront API ShopsBox -> DB ShopsBox
admin.shopsbox.ru -> backend ShopsBox -> DB ShopsBox
```

ShopsBox отвечает за админку и API. Клиент отвечает за свой frontend-хостинг, если нет отдельного договора.

### Вариант C: Own Infra Data

Клиент размещает БД и agent/API у себя.

```text
client-shop.ru -> витрина клиента или ShopsBox
agent.client-shop.ru -> agent/API клиента -> DB клиента
admin.shopsbox.ru -> platform API ShopsBox -> agent/API клиента
```

ShopsBox отвечает за админку/control plane и agent/API contract. Клиент отвечает за свой сервер, БД, бэкапы и runtime, если это не отдельная paid support услуга.

### Вариант D: Own Infra Full

Клиент размещает frontend, backend и БД у себя.

```text
client-shop.ru -> frontend клиента -> backend клиента -> DB клиента
admin.shopsbox.ru -> platform API ShopsBox -> agent/API клиента -> backend/DB клиента
```

ShopsBox дает пакет установки, agent/API, документацию и поддержку по договору.

## Production-пакет для клиента

Для Own Infra нужен не “архив с кодом”, а нормальный пакет поставки.

В составе:

- Docker Compose файл или другой согласованный runtime;
- backend service;
- storefront/frontend;
- database migrations;
- agent/API service;
- `.env.example`;
- инструкция по DNS;
- инструкция по SSL;
- инструкция по бэкапам;
- инструкция по обновлению;
- healthcheck endpoints;
- rollback-план;
- список портов и внешних зависимостей;
- описание границ ответственности.

Важно: production-пакет должен быть воспроизводимым. Если установку можно выполнить только “руками и по памяти”, такой Own Infra будет плохо поддерживать.

## API между админкой и клиентским контуром

Для Own Infra админка ShopsBox не должна ходить напрямую в БД клиента.

Коммуникация:

```text
ShopsBox Admin
  -> ShopsBox Platform API
  -> Client Agent/API
  -> Client Backend/DB
```

Минимальные возможности agent/API:

- регистрация агента;
- heartbeat;
- получение статуса;
- синхронизация каталога: товары, варианты, категории, изображения;
- синхронизация заказов: статусы, комментарии, служебные события;
- изменение настроек магазина;
- изменение настроек витрины;
- публикация конфигурации темы;
- прием команд управления;
- отправка событий;
- проверка версии;
- аудит команд.

Безопасность:

- токены с ограниченными правами;
- подписи запросов;
- rotate secrets;
- журнал действий;
- allowlist доменов/IP позже;
- версионирование API.

## Backend клиента как управляемый API

В Own Infra backend на стороне клиента нужен не как “еще один сайт”, а как управляемый API-слой над БД клиента.

Роль client backend/agent:

- принять команду из ShopsBox Platform API;
- проверить подпись и права;
- применить изменение к БД клиента;
- вернуть результат;
- записать локальный audit log;
- отправить событие обратно в ShopsBox.

Примеры команд:

- создать или обновить товар;
- изменить цену варианта;
- изменить остаток;
- изменить статус заказа;
- обновить настройки магазина;
- обновить настройки витрины;
- запросить healthcheck;
- сообщить версию установленного пакета.

Что нельзя делать:

- открывать прямой SQL-доступ из ShopsBox к БД клиента;
- выполнять произвольный код из админки;
- редактировать файлы клиента без отдельного deployment-механизма;
- смешивать команды управления магазином и поддержку сервера.

## Управление фронтом и стилями

Фронт тоже можно менять из админки, но не как “залезть в CSS клиента и править руками”. Безопасная модель:

```text
ShopsBox Admin
  -> настройки витрины / тема / блоки / цвета / логотип
  -> Platform API
  -> Client Agent/API или Storefront API
  -> storefront применяет опубликованную конфигурацию
```

Что можно поддержать в MVP/раннем этапе:

- логотип;
- основные цвета;
- контактные данные;
- меню;
- статические страницы;
- порядок блоков главной;
- SEO-поля;
- включение/скрытие товара и категории.

Что можно поддержать позже:

- темы;
- наборы блоков;
- кастомные CSS-переменные;
- предпросмотр;
- публикация черновик -> production;
- несколько storefront-каналов.

Правило:

> Админка меняет не произвольный код фронта, а конфигурацию витрины. Storefront сам применяет эту конфигурацию.

Если клиенту нужен полностью кастомный фронт, это уже кастомная разработка или Own Frontend. ShopsBox в таком случае отвечает за API/контракт, а не за каждый пиксель кастомного кода без отдельного договора.

Подробная продуктовая стратегия настройки витрины описана в [Стратегии настройки витрины](../product/08-storefront-customization-strategy.md).

## Перенос из демо в production

Нужно разделять:

- demo data;
- pilot data;
- production data.

Порядок:

1. Зафиксировать выбранную модель размещения.
2. Выгрузить настройки магазина.
3. Подготовить production runtime.
4. Применить миграции.
5. Импортировать каталог и настройки.
6. Настроить домен и SSL.
7. Подключить agent/API, если это Own Infra.
8. Проверить healthchecks.
9. Проверить checkout.
10. Зафиксировать дату перехода и rollback-план.

## Что заложить сейчас

В MVP не обязательно сразу делать полный автоматический перенос, но нужно не закрыть себе путь:

- хранить `store.slug` для поддоменов;
- держать `store.domain`;
- не смешивать demo/pilot/production статусы;
- заложить статус магазина;
- описать Storefront API;
- описать agent endpoints;
- описать настройки витрины как данные, а не как ручное редактирование CSS-файлов;
- делать миграции вместо ручных изменений БД;
- хранить audit logs;
- держать конфигурацию отдельно от кода.

## Простое объяснение клиенту

Сначала мы можем быстро показать магазин на поддомене ShopsBox. Если все подходит, выбираем production: оставить у нас в managed, подключить ваш домен или перенести фронт/БД/backend на ваш хостинг. ShopsBox при этом отвечает за админку и управление, а ответственность за серверы зависит от выбранной модели и договора.
