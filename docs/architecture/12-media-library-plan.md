# Медиатека магазина

Issue #50 описывает будущую медиатеку магазина: единый интерфейс управления изображениями, файлами и видео в кабинете владельца.

## Цель

Владелец магазина должен видеть все загруженные медиа в одном месте:

- изображения товаров;
- изображения витрины и будущего page builder;
- документы;
- будущие видео;
- неиспользуемые файлы;
- тяжелые файлы, влияющие на лимиты тарифа.

Медиатека должна быть связана с `FileStorage`, тарифными лимитами и учетом ресурсов.

## Граница MVP

В MVP медиатека должна работать с:

- изображениями товаров;
- обычными файлами, если они загружены через FileStorage;
- внешними ссылками на видео как metadata, без хранения тяжелых видео внутри ShopsBox.

Не нужно сразу:

- делать собственную видеоплатформу;
- transcoding;
- CDN;
- сложный DAM;
- шаринг файлов между магазинами.

## Модель

Базовая сущность будущей медиатеки: `media_assets`.

Минимальные поля:

- `id`;
- `tenant_id`;
- `store_id`;
- `storage_key`;
- `public_url`;
- `original_name`;
- `mime_type`;
- `media_type`: `image`, `document`, `video`, `other`;
- `size`;
- `uploaded_by_user_id` nullable;
- `created_at`;
- `deleted_at` nullable;
- `metadata` JSON.

Использование файла лучше хранить отдельно: `media_asset_usages`.

Поля usage:

- `id`;
- `media_asset_id`;
- `usage_type`: `product_image`, `page_builder_block`, `theme_logo`, `document_link`;
- `usage_id`;
- `created_at`.

Так можно безопасно понимать, где файл используется.

## Связь с FileStorage

`FileStorage` отвечает за физическое сохранение файла и public URL.

Медиатека отвечает за:

- запись metadata;
- привязку к tenant/store;
- отображение списка;
- фильтры;
- проверку использования перед удалением;
- связь с usage limits.

Application flow загрузки:

1. Controller получает файл.
2. Use case валидирует owner/store boundary.
3. Use case вызывает `FileStorage`.
4. Use case сохраняет `media_assets`.
5. Если файл сразу используется в товаре или блоке, создается `media_asset_usages`.

## Фильтры

Нужны фильтры:

- все;
- изображения;
- документы;
- видео;
- неиспользуемые;
- тяжелые файлы;
- загружено мной;
- по дате загрузки.

Тяжелый файл для MVP можно считать по простому порогу, например больше 10 МБ. Позже порог может зависеть от тарифа.

## Удаление

Удаление должно быть безопасным.

Правила:

- если файл используется товаром, страницей или настройками витрины, обычное удаление запрещено;
- UI должен показать, где используется файл;
- можно сделать отдельное действие `force delete`, но только после отдельного решения и логирования;
- физическое удаление из storage лучше делать после soft-delete metadata и проверки отсутствия usage.

На MVP достаточно:

- soft delete metadata;
- не показывать удаленный файл в списках;
- физическую очистку вынести в будущий maintenance job.

## Тарифные лимиты

Медиатека должна отдавать данные для лимитов:

- количество файлов;
- суммарный размер;
- размер по типам;
- размер неиспользуемых файлов;
- самые тяжелые файлы.

Эти данные связаны с будущими `resource_usage_daily` и `store_usage_limits`.

## Видео

На MVP видео не храним как тяжелые файлы внутри ShopsBox.

Допустимые варианты:

- внешняя ссылка на видео;
- lightweight metadata в `media_assets`;
- отдельный storage-сценарий позже.

Перед хранением видео внутри ShopsBox нужно отдельное решение по:

- лимитам;
- тарифам;
- обработке;
- CDN;
- legal/moderation.

## UI кабинета

Минимальный интерфейс:

- таблица или сетка файлов;
- превью для изображений;
- тип файла;
- размер;
- дата загрузки;
- кто загрузил;
- где используется;
- фильтры;
- действие удаления, если файл не используется.

## Проверки и тестовое покрытие

На этапе проектирования тесты не нужны.

При реализации нужны:

- unit-тест классификации `media_type` по mime type;
- unit-тест запрета удаления используемого файла;
- integration-тест store boundary;
- integration-тест подсчета размера файлов;
- functional-тест списка медиатеки;
- functional-тест удаления неиспользуемого файла;
- functional-тест отказа удаления используемого файла.
