# Правила разработки на Symfony

## Главная мысль

Пишем не "как ИИ", а как нормальный разработчик, которому потом самому поддерживать проект и объяснять его на собеседовании.

Архитектура должна помогать понимать код. Если слой, интерфейс или паттерн не помогает объяснить систему проще, его не добавляем.

Отдельное правило: владелец проекта сейчас изучает Symfony, поэтому после крупных внедрений нужно объяснять изменения как ментор. Не ограничиваться списком файлов.

## Как объяснять проект

Базовая фраза:

> Symfony у нас отвечает за HTTP, DI, консольные команды, миграции и инфраструктурную обвязку. Бизнес-сценарии лежат в application-слое, доменные правила в domain-слое, работа с БД и внешними сервисами в infrastructure-слое.

Эта фраза должна оставаться правдой по мере разработки.

## Формат менторского объяснения после крупной задачи

После заметного внедрения нужно дать короткий разбор:

1. Что добавили с точки зрения продукта.
2. Какие файлы и папки появились.
3. Как запрос проходит по слоям: Controller -> Command/Query -> Handler -> Domain -> Repository -> Database.
4. Что здесь делает Symfony, а что является нашей бизнес-логикой.
5. Какие места важно запомнить для собеседования.
6. Что можно будет упростить или переделать позже, если станет неудобно.

Формат объяснения должен быть человеческий, без академической воды. Цель - чтобы владелец проекта мог открыть код и понять, почему он устроен именно так.

## Слои

### Domain

Что здесь живет:

- сущности домена;
- value objects;
- доменные правила;
- доменные события, если они реально нужны;
- интерфейсы репозиториев, когда домен не должен знать о Doctrine.

Что сюда не класть:

- Symfony Request/Response;
- Doctrine QueryBuilder;
- контроллеры;
- формы;
- сериализацию API;
- работу с внешними HTTP API.

Пример:

```text
src/Catalog/Domain/Product.php
src/Catalog/Domain/ValueObject/ProductStatus.php
src/Catalog/Domain/Repository/ProductRepository.php
```

### Application

Что здесь живет:

- use cases;
- команды и query-модели;
- DTO входа/выхода;
- orchestration: загрузить сущность, вызвать доменное правило, сохранить, отправить событие;
- транзакционные сценарии.

Что сюда не класть:

- SQL руками без причины;
- HTML/Twig;
- Symfony Controller;
- сложные Doctrine entity tricks;
- знание о конкретном transport-слое.

Пример:

```text
src/Catalog/Application/CreateProduct/CreateProductCommand.php
src/Catalog/Application/CreateProduct/CreateProductHandler.php
```

### Infrastructure

Что здесь живет:

- Doctrine mappings/repositories;
- реализации repository-интерфейсов;
- интеграции с оплатами, доставками, S3, почтой;
- реализации очередей и внешних clients;
- техническое хранение файлов.

Пример:

```text
src/Catalog/Infrastructure/Doctrine/DoctrineProductRepository.php
src/Order/Infrastructure/Payment/YooKassaPaymentGateway.php
```

### Interface

Что здесь живет:

- HTTP controllers;
- console commands;
- API request/response transformers;
- webhook controllers;
- admin endpoints.

Контроллер должен быть тонким:

1. Принять HTTP-запрос.
2. Собрать command/query.
3. Вызвать handler.
4. Вернуть response.

Если в контроллере появляются бизнес-правила, значит код уехал не туда.

Пример:

```text
src/Catalog/Interface/Http/Admin/CreateProductController.php
src/Order/Interface/Http/Storefront/CheckoutController.php
```

## Модули

Проект лучше делить по доменным зонам, а не по техническим папкам на весь проект.

Предварительный формат:

```text
src/
  Catalog/
    Domain/
    Application/
    Infrastructure/
    Interface/
  Order/
    Domain/
    Application/
    Infrastructure/
    Interface/
  Tenant/
    Domain/
    Application/
    Infrastructure/
    Interface/
```

Так проще объяснять: "все по каталогу лежит в Catalog", а внутри уже видно слои.

## Symfony best practices для проекта

- Использовать autowiring и DI Symfony, но не прятать важные зависимости.
- Валидацию входных данных держать рядом с command/request DTO, а доменные инварианты - в домене.
- Doctrine migrations обязательны для изменения схемы.
- Repository не должен превращаться в свалку бизнес-операций.
- Service-классы не называть абстрактно `Manager`, `Helper`, `Processor`, если можно назвать по сценарию: `CreateProductHandler`, `ReserveInventoryHandler`.
- Не создавать base-классы и traits заранее.
- Не добавлять event bus, CQRS, hexagonal ports везде подряд, пока нет реальной боли.
- Тестировать прежде всего доменные правила и application use cases.

## Doctrine и быстрые запросы

Doctrine Migrations используем для изменений схемы БД. Это не runtime-нагрузка на обычные запросы пользователя.

Doctrine ORM используем прагматично:

- обычные CRUD-сценарии админки;
- загрузка и сохранение доменных сущностей;
- понятные связи, которые легко объяснить;
- места, где важнее поддерживаемость, чем максимальная скорость.

Doctrine ORM не используем как молоток для всего:

- массовый импорт товаров;
- массовое обновление цен и остатков;
- сложные отчеты;
- hot path резервирования остатков;
- тяжелые списки с агрегациями.

Для таких мест используем Doctrine DBAL или native SQL внутри infrastructure/repository слоя. Снаружи application-слой все равно видит нормальный репозиторий или query service, а не SQL прямо в use case.

Cycle ORM или Active Record не добавляем в MVP. Второй ORM рядом с Doctrine усложнит обучение Symfony, DI, транзакции и объяснение проекта. Вернуться к этому можно только после реального профилирования и понятной боли.

## Простая схема запроса

```text
HTTP request
  -> Controller
  -> Command/Query
  -> Handler
  -> Domain model
  -> Repository interface
  -> Doctrine repository
  -> Database
```

## Пример объяснения на собеседовании

> В проекте я разделил Symfony и бизнес-логику. Контроллеры тонкие: они принимают запрос и вызывают use case. Use case находится в application-слое и описывает конкретный сценарий, например создание товара или смену статуса заказа. Доменные правила лежат в domain-слое, поэтому они не зависят от HTTP и Doctrine. Infrastructure отвечает за Doctrine, платежные системы, доставку и файловое хранилище. Так проект проще тестировать и проще переносить между web, mobile и desktop-клиентами.

Важно: на собеседовании не нужно рассказывать, что схема "взята" из чужих продуктов. Лучше объяснять это как собственное инженерное решение: какие сущности есть, за что отвечают слои, почему контроллеры тонкие, почему склад отделен от товара.

## Что можно упростить в MVP

На старте не нужно делать идеальную академическую архитектуру:

- можно начать с одного backend-приложения Symfony;
- можно не вводить отдельный read model слой, пока нет сложных отчетов;
- можно использовать Doctrine entity как доменную сущность для простых CRUD-частей;
- можно добавлять интерфейсы репозиториев только в тех местах, где есть бизнес-логика или нужна подмена реализации;
- можно отложить доменные события до сценариев, где они реально упрощают код.

Главное: не смешивать HTTP, SQL, бизнес-правила и интеграции в одном классе.
