# ТЗ: черновик

## Назначение системы

Создать платформу ShopsBox для запуска и управления интернет-магазинами. Платформа должна позволять быстро выдавать клиенту рабочий магазин под ключ, а также поддерживать сценарий, при котором данные и фронт клиента находятся на его инфраструктуре.

## Основные роли

- Покупатель: просматривает витрину, добавляет товары в корзину, оформляет заказ.
- Владелец магазина: управляет товарами, заказами, клиентами, настройками и интеграциями.
- Сотрудник магазина: работает с ограниченными правами.
- Оператор платформы: управляет клиентами, магазинами, тарифами и инфраструктурой.
- Технический администратор: обслуживает деплой, бэкапы, логи и восстановление.

## Режимы размещения

### Managed Store

Основной режим. Платформа предоставляет и обслуживает магазин полностью:

- backend;
- база данных;
- web-витрина;
- админка;
- SSL;
- домен или подключение домена клиента;
- бэкапы;
- обновления;
- мониторинг;
- поддержка.

### Own Infra

Расширенный режим. На инфраструктуре клиента размещается часть системы:

- storefront;
- база;
- backend или agent/API;
- интеграционные адаптеры при необходимости.

SaaS-админка управляет магазином через защищенный API/agent. Прямой доступ к базе клиента не является базовым вариантом.

### Self-hosted Licensed

Будущий коробочный режим. Клиент получает ShopsBox как пустой Docker-дистрибутив, разворачивает его на своей инфраструктуре, подключает свою БД или БД из дистрибутива и использует license file/license key. Коробка продается целиком без деления на платные модули, а демо-данные переносятся отдельным скриптом импорта.

ShopsBox в этом режиме отвечает за продукт, Docker image, миграции, обновления и поддержку по договору. Клиент отвечает за сервер, сеть, БД, бэкапы, SSL и мониторинг, если отдельным договором не указано другое.

Лицензия должна привязываться к production-домену, instance id и разрешенному числу production/staging/dev активаций. Один license key не должен запускать несколько production-доменов без расширения лицензии.

## Функциональные блоки MVP

- Регистрация клиента и создание магазина оператором платформы.
- Управление товарами.
- Управление категориями.
- Загрузка изображений товаров.
- Управление заказами.
- Базовые статусы заказов.
- Управление покупателями.
- Настройки магазина.
- Подключение домена.
- SSL.
- Бэкапы.
- Роли сотрудников.
- Журнал действий.
- Простая публичная витрина.

## Нефункциональные требования

- Код backend должен строиться по Clean Architecture и DDD.
- Бизнес-логика не должна жить в контроллерах.
- Внешние интеграции должны подключаться через интерфейсы/адаптеры.
- Система должна поддерживать multi-tenancy.
- Каждое действие в админке, влияющее на бизнес-данные, должно логироваться.
- MVP должен запускаться через Docker Compose.
- Архитектура не должна блокировать будущий переход к Kubernetes.
- Web MVP должен использовать Twig + Bootstrap.
- React + TypeScript не входит в первый MVP и рассматривается как будущий вариант для сложных экранов или SPA-админки.
- Backend API должен проектироваться так, чтобы его могли использовать будущие mobile и desktop-клиенты.

## Принятые решения для первого MVP

- Первый режим размещения: Managed Store.
- Поддомен ShopsBox используется для демо, пилота, каталога и тестовой оплаты; боевой эквайринг на поддомене ShopsBox не является базовым сценарием.
- Для production-платежей базовый путь - домен или поддомен клиента, merchant/терминал клиента, реквизиты клиента-продавца и его онлайн-касса.
- Own Infra остается в архитектуре как будущий расширенный сценарий через защищенный API/agent, а не через прямой доступ SaaS к базе клиента.
- Self-hosted Licensed остается в архитектуре как будущий коробочный сценарий через Docker-дистрибутив и лицензию, но не входит в первый MVP.
- Backend: PHP + Symfony.

## Модерация товаров на поддомене ShopsBox

Техническая ссылка магазина предназначена только для владельца магазина, сотрудников магазина, модераторов и администраторов платформы. Она используется для настройки, предпросмотра и модерации, но не является публичной витриной и не должна открываться покупателям без авторизации.

Публичный поддомен `*.shopsbox.ru` включается только после выбора имени поддомена, подтверждения email, подтверждения российского мобильного телефона, заполнения ФИО владельца и принятия соглашения об ответственности за размещаемые товары и контент.

Телефон для публикации на поддомене ShopsBox на этапе MVP принимается только в формате российского мобильного номера `+79XXXXXXXXX`. Номер должен быть подтвержден одноразовым кодом, а факт подтверждения нужно хранить с датой, IP, user agent и используемым провайдером отправки кода.

Для магазинов на поддомене ShopsBox первая публикация товара требует премодерации оператором платформы.

После одобрения повторная премодерация нужна только при изменении публичного названия, публичного описания или изображений товара. Изменение категории, SEO-полей, характеристик, дополнительных полей, цены, остатка, артикула, сортировки и статуса наличия на этапе MVP не отправляет товар на повторную модерацию.

Для магазина на своем домене в managed SaaS базовый режим мягче: товаром управляет владелец магазина, а ShopsBox оставляет за собой право автоматической проверки, ручной постмодерации и блокировки товара или магазина при нарушении правил сервиса или закона.
- Web MVP: Twig + Bootstrap, точечная интерактивность через Stimulus или простой JavaScript.
- База данных: PostgreSQL.
- Миграции: Doctrine Migrations.
- ORM: Doctrine ORM для обычных CRUD-сценариев.
- Быстрые и сложные запросы: Doctrine DBAL/native SQL внутри infrastructure-слоя, когда это реально нужно.
- Runtime разработки и MVP-контура: Docker Compose через `make`-команды.
- Multi-tenancy MVP: shared app + shared DB + `tenant_id` / `store_id`.
- React + TypeScript, Kotlin Multiplatform, Kubernetes и отдельные DB/schema на магазин не входят в первый MVP.
- Интеграция с 1С не входит в первый MVP, но фиксируется как дальнее стратегическое направление после отдельного исследования и локального тестового контура 1С.
- Бесплатные тарифы managed-контура могут монетизироваться через Яндекс Рекламу: рекламные блоки показываются в админке клиента и на публичной витрине магазина. В платных тарифах реклама отключается. На витрине реклама не должна появляться в корзине, checkout, оплате и местах, где она мешает покупке.
