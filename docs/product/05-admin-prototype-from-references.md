# Прототип админки на основе аналогов

Документ фиксирует, как мы берем структуру сильных ecommerce-админок и переделываем ее под ShopsBox. Это не финальный UI-макет, а продуктовый прототип страниц: что должно быть в меню, какие экраны нужны в MVP и какие идеи оставляем на потом.

## Что уже взяли

Из Shopify берем понятную центральную админку: home/dashboard, заказы, товары, клиенты, аналитика, скидки, каналы продаж, приложения и настройки. Важная идея для ShopsBox: владелец магазина должен начинать день с задач и метрик, а не с абстрактной панели.

Из Medusa берем операционную структуру commerce-admin: продукты, заказы, инвентарь, склады, pricing, promotions, customers, regions/channels/settings. Важная идея для ShopsBox: склад и каналы продаж не прятать внутри товара, а показать отдельными рабочими зонами, когда это станет нужно.

Из Saleor берем API-first и разделение core concepts: products, checkout, channels, promotions, payments, extensions/apps. Важная идея для ShopsBox: даже если первый web MVP на Twig, backend и сценарии должны быть готовы к mobile/desktop и Own Infra.

Из Sylius берем Symfony-ориентир: admin panel как набор ресурсов, grids для списков, отдельные sales/configuration зоны, channels, roles/RBAC и возможность расширять admin без смешивания бизнес-логики с UI.

## Принцип ShopsBox

ShopsBox не копирует меню аналогов один-в-один. Мы берем структуру, которую владелец магазина сможет объяснить простыми словами:

```text
Сегодня
Продажи
Каталог
Склад
Клиенты
Маркетинг
Витрина
Настройки
Техника
Поддержка
```

Для MVP часть разделов будет заглушкой или упрощенной страницей. Важно, чтобы структура не ломалась, когда появятся скидки, платежи, доставки, несколько каналов продаж и Own Infra.

## Админка владельца магазина

### Сегодня

Назначение: стартовая страница владельца магазина.

MVP-содержимое:

- продажи за сегодня / 7 дней / 30 дней;
- новые заказы;
- заказы, требующие действия;
- товары с низким остатком;
- предупреждения по домену, SSL и бэкапам;
- быстрые действия: добавить товар, открыть заказы, создать обращение.

Позже:

- настраиваемые метрики;
- инсайты и подсказки;
- виджеты каналов продаж.

### Заказы

Назначение: ежедневная операционная работа.

Страницы:

- список заказов;
- карточка заказа;
- изменение статуса;
- комментарии и история;
- платежи и доставка;
- возвраты и отмены позже.

В карточке заказа должны быть видны: номер, статус, покупатель, товары, сумма, оплата, доставка, история действий, технические события.

### Каталог

Назначение: управление тем, что продается.

Страницы:

- список товаров;
- создание товара;
- редактирование товара;
- варианты товара;
- изображения;
- категории и коллекции;
- импорт/экспорт позже.

В карточке товара нужны блоки: название, описание, статус публикации, категории, изображения, варианты, SKU, цена, остатки, SEO. Остатки показываем как связанный блок, но складскую логику не смешиваем с описанием товара.

### Склад

Назначение: управлять наличием и резервами.

MVP-содержимое:

- остатки по товарам;
- остатки по складам;
- ручная корректировка;
- резервы;
- предупреждения о низком остатке.

Позже:

- несколько складов;
- incoming quantity;
- bulk update;
- движения склада.

### Клиенты

Назначение: видеть покупателей и историю отношений.

Страницы:

- список клиентов;
- карточка клиента;
- адреса;
- заказы клиента;
- заметки и сегменты позже.

### Маркетинг

Назначение: не перегружать MVP, но оставить место для роста.

MVP:

- промокоды и скидки как отложенный раздел;
- простые акции позже, после базовых заказов и каталога.

Позже:

- автоматические скидки;
- сегменты клиентов;
- кампании;
- рекомендации.

### Витрина

Назначение: управлять тем, что видит покупатель.

MVP:

- главная;
- меню;
- статические страницы;
- настройки публикации товара;
- базовые SEO-поля.

Позже:

- темы;
- блоки главной;
- предпросмотр;
- несколько storefront-каналов.

### Настройки

Назначение: базовые параметры магазина.

Разделы:

- профиль магазина;
- домены;
- валюта и часовой пояс;
- пользователи и роли;
- каналы продаж;
- оплаты;
- доставки;
- тариф и биллинг.

В MVP платежи и доставки можно начать с ручных способов, чтобы не блокировать первый checkout сложными интеграциями.

### Техника

Назначение: сделать managed hosting частью продукта, а не скрытой инфраструктурой.

MVP:

- статус домена;
- SSL;
- последние бэкапы;
- healthchecks backend/DB;
- журнал действий.

Позже:

- восстановление из бэкапа;
- логи интеграций;
- версия магазина;
- Own Infra agent status.

### Поддержка

Назначение: дать владельцу понятный канал помощи.

MVP:

- создать обращение;
- указать магазин и проблему;
- приложить технический контекст: домен, последний бэкап, статус сервисов.

Позже:

- история обращений;
- SLA;
- чат.

## Супер-админка платформы

Супер-админка не должна выглядеть как магазинная админка с лишними кнопками. Это рабочее место оператора ShopsBox.

MVP-разделы:

- Клиенты: tenants, контакты, статус, тариф.
- Магазины: список stores, домены, статус, дата последнего бэкапа.
- Операции: создать бэкап, проверить healthcheck, запустить восстановление позже.
- Пользователи: операторы платформы и доступы.
- Поддержка: обращения клиентов.
- Аудит: действия владельцев, сотрудников и операторов.
- Настройки платформы: тарифы, лимиты, системные параметры.

Позже:

- управление версиями магазинов;
- Own Infra agents;
- billing automation;
- отчеты по инфраструктуре.

## Публичная витрина

Для первого MVP витрина должна быть простой и не конкурировать с конструктором тем.

Страницы:

- главная;
- каталог;
- категория;
- товар;
- корзина;
- checkout;
- успешный заказ;
- доставка;
- оплата;
- контакты;
- политика конфиденциальности.

Первый прототип витрины должен проверять не дизайн, а поток: найти товар -> выбрать вариант -> добавить в корзину -> оформить заказ -> получить номер заказа.

## Что не делать в первом MVP

- Не строить marketplace расширений.
- Не делать сложный visual theme builder.
- Не делать GraphQL обязательным интерфейсом.
- Не делать много складов обязательным сценарием для первого магазина.
- Не делать маркетинг и автоматизации раньше базового каталога, заказов и checkout.
- Не смешивать настройки магазина, технический статус и поддержку в одну страницу.
