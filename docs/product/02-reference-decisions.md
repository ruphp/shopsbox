# Решения, которые берем в основу

Этот документ фиксирует, какие хорошие идеи берем из существующих ecommerce/backoffice-продуктов и как адаптируем их под ShopsBox.

## Главный стартовый выбор

Начинаем не с "убийцы Shopify" и не с абстрактной headless-платформы. Начинаем с managed store:

> Клиент получает магазин под ключ, данные и магазин можно забрать/перенести, техническую часть ведем мы.

Для простых клиентов это должно ощущаться как готовый сервис. Для продвинутых клиентов позже будет Own Infra через agent/API.

## Что берем от Shopify

Берем:

- простую и понятную админку для владельца магазина;
- быстрый старт магазина без технических знаний;
- единый центр управления товарами, заказами, клиентами и настройками;
- тарифную модель;
- экосистемное мышление: потом можно добавить темы, приложения, интеграции.

Не берем в MVP:

- сложный marketplace приложений;
- большой конструктор тем;
- десятки интеграций сразу;
- полную закрытость и жесткий vendor lock-in.

Как объяснять:

> У нас похожая ценность для клиента: не думать о технике. Но мы делаем сильный акцент на переносимость и возможность отдельной инфраструктуры.

## Что берем от WooCommerce / OpenCart / self-hosted платформ

Берем:

- ощущение владения магазином и данными;
- возможность переносить сайт и базу;
- понятную модель "мой магазин, мои данные";
- гибкость кастомизации.

Не берем в MVP:

- хаотичную плагинную систему;
- зависимость от ручной настройки хостинга клиентом;
- ситуацию, где клиент сам отвечает за обновления и безопасность.

Как объяснять:

> Клиенту не нужно самому администрировать хостинг, но он не должен чувствовать, что магазин навсегда заперт внутри нашей платформы.

## Что берем от headless/composable commerce

Берем:

- API-first подход;
- разделение админки, backend и витрины;
- возможность иметь web, mobile и desktop-клиентов поверх одного API;
- возможность сделать разные storefront-приложения для разных клиентов.

Не берем в MVP:

- чрезмерную микросервисность;
- сложные event-driven схемы без необходимости;
- Kubernetes как обязательное условие;
- отдельную команду DevOps как требование для запуска.

Как объяснять:

> Мы проектируем API-first, чтобы потом подключить мобильные приложения и Own Infra, но не усложняем первый релиз микросервисами.

## Что берем от Medusa / Saleor

Берем:

- идею современного ecommerce backend;
- чистую API-модель;
- отделение витрины от core;
- возможность кастомизации под конкретный бизнес.

Не берем в MVP:

- попытку сразу повторить весь framework;
- слишком широкую модель расширений;
- GraphQL как обязательный выбор до понимания нужд проекта.

Как объяснять:

> Нам важна не модность headless, а возможность строить разные клиентские интерфейсы поверх одного ядра.

## Что берем от Forest Admin / Retool

Берем:

- идею central control plane;
- admin UI как отдельный слой управления;
- сценарий подключения к инфраструктуре клиента через agent/API;
- осторожность с прямым доступом к базе клиента.

Не берем в MVP:

- универсальный конструктор любых админок;
- прямую генерацию интерфейса из БД как основную модель;
- доступ SaaS-админки напрямую к клиентской базе.

Как объяснять:

> Для Own Infra наша админка должна управлять магазином через защищенный агент, а не лазить напрямую в базу клиента.

## Инженерные принципы MVP

Для первого релиза фиксируем практичный инженерный подход:

- стабильный backend API и web-админка важнее раннего mobile/desktop направления;
- бизнес-логика не должна жить в контроллерах;
- Docker Compose и `make` остаются основным локальным контуром;
- долгосрочные решения фиксируются в документации;
- временные компромиссы явно помечаются и имеют условие пересмотра;
- код должен оставаться понятным, объяснимым и привязанным к конкретным задачам.

## Итоговая стратегия MVP

1. Managed Store как основной сценарий.
2. Symfony backend как модульный монолит.
3. Web MVP на Twig + Bootstrap, с точечной интерактивностью через Stimulus/vanilla JS.
4. PostgreSQL как основная БД.
5. Docker Compose через make.
6. FrankenPHP как стартовый app server.
7. Thin controllers, use cases, понятные domain-модули.
8. GitHub Issues, Pull Requests и milestones для управления работой.
9. Текстовые прототипы и Mermaid вместо Figma на первом этапе.
10. Own Infra через agent/API как будущая расширенная опция.
11. API проектируем аккуратно, чтобы позже подключить mobile/desktop и при необходимости отдельный React/TS frontend.
12. Doctrine ORM используем для обычных сценариев, Doctrine DBAL/native SQL - для тяжелых и быстрых запросов.

## Что делаем первым

Первым нужно подготовить проектные решения и задачи:

- выбрать multi-tenant стратегию MVP;
- выбрать формат Symfony skeleton;
- зафиксировать Twig + Bootstrap как frontend MVP;
- описать первые GitHub issues;
- описать текстовые прототипы ключевых экранов админки;
- описать минимальную модель каталога и заказов;
- подготовить Docker Compose контур под Symfony, FrankenPHP, PostgreSQL и Redis.
