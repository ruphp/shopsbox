# Правила работы над ShopsBox

Эти правила обязательны для AI-агентов, разработчиков и автоматизаций, работающих в проекте.

## Базовый принцип

Проект должен развиваться как понятная инженерная система, а не как набор случайных правок. Любое заметное изменение должно быть связано с задачей, доменной областью и проверяемым результатом.

## Документация перед кодом

- Перед крупной разработкой сначала обновлять ТЗ, архитектурный документ или backlog.
- Не добавлять временные личные заметки в долговременную документацию.
- Долговременные решения фиксировать в `docs/`, `CONTEXT.md` и `AGENTS.md`.
- Если решение временное, явно помечать его как временное и указывать условие пересмотра.
- После крупных внедрений давать владельцу проекта короткое менторское объяснение: что изменилось, где это лежит, как работает по слоям и как это можно объяснить на собеседовании.

## Runtime и инфраструктура

- Docker Compose считается основным runtime-контуром MVP.
- Не рассчитывать на локальный PHP, Composer, Node или Kotlin runtime как на источник истины.
- Все проектные операции выполнять через `make`-команды.
- PowerShell не использовать как рабочую среду проекта, потому что он регулярно ломает кириллицу и многострочный текст.
- PowerShell допустим только как транспорт для запуска `make`, если другого способа в текущей среде нет.
- Не передавать через PowerShell heredoc, многострочный JSON, русские тексты issue/PR/comment или сложные GitHub API payloads. Для таких операций сначала создать UTF-8 файл в репозитории и вызвать его через `make`-цель.
- Если агент начал писать прямую PowerShell-команду для проектной операции, нужно остановиться и добавить/использовать `make`-обертку.
- Если для задачи нужна локальная среда, сначала добавить или обновить `make`-команду, а уже внутри нее использовать Docker Compose, Gradle wrapper или проектные скрипты.
- Прямые команды `docker compose`, `php`, `composer`, `npm`, `gradle`, `gh` и подобные не запускать вручную, если для них можно сделать `make`-обертку.
- Схему базы данных менять только миграциями.
- Бэкапы, healthchecks и восстановление считать частью продукта, а не "потом когда-нибудь".

## Архитектура backend

- Основной backend: PHP + Symfony.
- Архитектурный стиль: Clean Architecture, DDD, SOLID.
- Backend развивается как модульный монолит: один Symfony backend, модули по доменным областям, без микросервисов на MVP.
- Для задачи `#2` создавать только модуль `Tenant`, не заводить заранее `Catalog`, `Order`, `Billing` и другие пустые модули.
- Структура модуля: `Domain`, `Application`, `Infrastructure`, `Presentation`.
- Бизнес-логика не должна жить в контроллерах.
- Контроллеры принимают запрос, вызывают application use case и возвращают ответ.
- Доменная логика живет в Domain/Application слоях.
- Presentation может собрать DTO из HTTP-запроса или формы, но сам класс DTO для сценария должен лежать в Application/Dto.
- DTO для сценариев держать в Application/Dto, а контракты внешних действий - в Application/Contracts; не плодить вложенность по одному use case без необходимости.
- Application/Contracts вызываются из Application/UseCase; Presentation не дергает эти контракты напрямую без отдельного архитектурного обоснования.
- Внешние сервисы подключаются через интерфейсы и infrastructure-адаптеры.
- Multi-tenancy учитывать с самого начала.
- Писать как разработчик, а не как ИИ: меньше искусственных абстракций, больше понятных классов с ясной ответственностью.
- Не плодить интерфейсы "на всякий случай". Интерфейс нужен, когда есть внешний адаптер, тестовая подмена или реальная вариативность реализации.
- Symfony использовать как framework-обвязку, а не как место для всей бизнес-логики.
- Doctrine entity не должна автоматически становиться всей доменной моделью, если внутри появляется сложное правило.
- Названия классов, use case и методов должны быть такими, чтобы владелец проекта мог объяснить их на собеседовании.

## Архитектура клиентов

- Web-админка должна проектироваться API-first, чтобы ее сценарии можно было переиспользовать в mobile/desktop.
- Kotlin Multiplatform рассматривается как стратегическая база для Android/iOS и потенциально Windows desktop.
- KMP не должен блокировать запуск web MVP.
- Конфигурацию клиентов нужно отделять от кода: режимы local/remote, URL API, feature flags.

## GitHub workflow

- Рабочий процесс ведется через GitHub Issues, Pull Requests, Milestones и Project board.
- Trello не используем.
- Figma не используем как обязательный этап; вместо нее допускаются текстовые прототипы, схемы Mermaid и позже HTML-прототипы.
- Перед началом содержательной задачи проверять, есть ли под нее issue.
- Для отдельной фичи или архитектурного изменения создавать task-ветку.
- После локальной реализации и проверки делать стоп и показывать статус.
- GitHub CLI вызывать через `make`-команды, особенно если команда передает русский текст.
- Русский текст для issue/PR/comment передавать через UTF-8 файлы, а не через сырой многострочный ввод в PowerShell.
- Без явного отдельного подтверждения нельзя делать `push`, создавать `PR`, делать `merge`, закрывать issue или переводить карточку в Done.
- Фразы "делай дальше", "действуй", "заверши" не считаются разрешением на удаленные действия.

## Статусы задач

- Backlog: задача описана, но работа не начата.
- Ready: задача понятна и готова к реализации.
- In progress: работа реально идет локально или в ветке.
- In review: открыт PR или идет проверка.
- Done: задача смержена, проверена и закрыта.

## Проверки

- В конце каждой issue обязательно фиксировать решение по тестовому покрытию: какие unit, integration или functional tests нужны, какие миграции и Docker-проверки запускались, либо почему новые тесты не нужны.
- Нельзя закрывать issue без короткого вывода по проверкам и тестам в финальном отчете или PR.
- Если тесты не запускались, это обязательно указывать в финальном отчете.
- Для изменений в доменной логике добавлять или обновлять тесты.
- Для изменений БД проверять миграции.
- Для инфраструктурных изменений проверять локальный Docker Compose контур.

## Анти-сложность

- Не усложнять проект "модной архитектурой" без практической пользы.
- Любое решение должно быть объяснимо человеческим языком владельцу проекта.
- Kubernetes, микросервисы, marketplace расширений и полная mobile/desktop экосистема не являются задачами первого MVP.
- После сложного изменения обновлять документацию слоя или сценария, чтобы проект можно было быстро вспомнить и объяснить.
- Если Symfony-решение требует знания framework-магии, рядом нужно оставить объяснение простыми словами: какой класс за что отвечает и почему он находится именно в этом слое.
